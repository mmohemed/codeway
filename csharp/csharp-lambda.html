تعبيرات Lambda

Lambda Expressions, Closures & Expression Trees

تعبيرات Lambda هي الصيغة المختصرة للمفوضيات — تلك الأسهم الصغيرة x => x * 2 التي تراها في كل مكان في C# الحديث. تعلم كيف تكتبها، وكيف تعمل داخلياً، وكيف تستخدم الإغلاقات لتبسيط كودك.

ما هي تعبيرات Lambda؟ WHAT ARE LAMBDA EXPRESSIONS?

تعبير Lambda هو صيغة مختصرة لتعريف دالة مجهولة (Anonymous Function) — أي دالة بدون اسم، تُستخدم في مكانها مباشرة. بدلاً من كتابة دالة كاملة وتعريف مفوضية وإسنادها، تكتب تعبيراً صغيراً بسهم => (يُقرأ "goes to") يفصل المعاملات عن الجسم.

تخيل أنك تريد تمرير دالة إلى Where أو Sort. بدون Lambda، تحتاج كتابة دالة كاملة أو استخدام delegate قديم. مع Lambda، كل شيء في سطر واحد واضح.

C# — التطور من الدالة الكاملة إلى Lambda 
// 1. الطريقة القديمة: دالة كاملة
static int Square(int x) => x * x;
Func<int, int> f = Square;

// 2. دالة مجهولة قديمة (anonymous method)
Func<int, int> f2 = delegate(int x) { return x * x; };

// 3. تعبير Lambda — الصيغة الحديثة
Func<int, int> f3 = x => x * x;

الفرق الجوهري: delegate { } القديمة كانت تحتاج كلمة return دائماً. تعبير Lambda يستخدم => ويسمح بالصيغة التعبيرية (سطر واحد) أو الصيغة الكتلية (أقواس { }).

تعبير Lambda ليس نوعاً بحد ذاته. إنه يُترجم تلقائياً إلى مفوضية (Action، Func، Predicate) أو إلى شجرة تعبير (Expression<T>) حسب السياق. هذا ما يسمى Target Typing.

الأشكال الأربعة للكتابة THE FOUR SYNTAX FORMS

تعبير Lambda يمكن كتابته بأربعة أشكال حسب عدد المعاملات وحجم الجسم. إتقان هذه الأشكال يجعلك تقرأ كود الآخرين بسرعة:

1. بدون معاملات

() => Console.WriteLine("hi")

تُستخدم مع Action أو Func<TResult>.

2. معامل واحد

x => x * 2

يمكن حذف الأقواس حول معامل واحد.

3. معاملات متعددة

(a, b) => a + b

الأقواس إلزامية.

4. جسم كتلي

x => { return x * 2; }

الأقواس والـ return إلزاميان.

الشكل مثال النوع المقابل
بدون معاملات () => DateTime.Now Func<DateTime>
معامل واحد بسيط x => x > 0 Func<int, bool>
معاملان (a, b) => a + b Func<int, int, int>
جسم كتلي x => { Console.WriteLine(x); } Action<int>

أمثلة تطبيقية على الأشكال الأربعة

C# — Four Forms in Practice 
// 1. بدون معاملات — Action لا يرجع شيئاً
Action greet = () => Console.WriteLine("مرحباً!");
greet();

// 2. معامل واحد — Func يرجع قيمة
Func<int, int> square = x => x * x;
Console.WriteLine(square(5));  // 25

// 3. معاملان — يجمع رقمين
Func<int, int, int> add = (a, b) => a + b;
Console.WriteLine(add(3, 4));  // 7

// 4. جسم كتلي — منطق معقد
Func<int, string> classify = n =>
{
    if (n > 0) return "موجب";
    if (n < 0) return "سالب";
    return "صفر";
};

ملاحظة على الأنواع الضمنية: في Lambda، المترجم يستنتج نوع المعاملات من المفوضية المستهدفة. لكن لا يمكنك استخدام var مع Lambda نفسها — يجب تحديد نوع المفوضية أولاً: Func<int, int> f = x => x * 2; وليس var f = x => x * 2;.

3

الإغلاقات — Closures CAPTURED VARIABLES

الإغلاق (Closure) هو أحد أقوى مفاهيم Lambda — وأكثرها إثارة للارتباك. عندما تكتب تعبير Lambda يستخدم متغيراً معرّفاً خارج نفسه، فإن Lambda "تأسر" (capture) هذا المتغير وتحتفظ به حياً طوال عمرها. ليس نسخة منه، بل المتغير نفسه.

هذا يعني أن Lambda يمكنها تعديل المتغير الأصلي، وأن المتغير يبقى محفوظاً حتى لو انتهى نطاقه (Scope) الأصلي. هذه القوة العظيمة تأتي مع مسؤولية عظيمة — وأخطاء دقيقة جداً.

C# — Closure Basic 
public static Func<int> CreateCounter()
{
    int count = 0;

    // Lambda تأسر count (المرجع، لا النسخة)
    return () => ++count;
}

var counter = CreateCounter();
Console.WriteLine(counter()); // 1
Console.WriteLine(counter()); // 2
Console.WriteLine(counter()); // 3

// count حي رغم انتهاء نطاق CreateCounter
// Lambda تحافظ على المتغير "مُعلّقاً" في الذاكرة

كيف يحدث ذلك تقنياً؟ المترجم ينشئ فئة مخفية (Closure Class) تحتوي على المتغير المُأسَر. Lambda تصبح دالة في هذه الفئة، والمتغير يصبح حقلاً في الكائن. لا سحر — مجرد فئة يولّدها المترجم.

الفخ الشهير: المتغير في حلقة For

C# — Classic Closure Bug 
// ❌ خطأ شائع في foreach قبل C# 5 (وفي for دائماً)
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));

// ستظن الناتج: 0 1 2 — لكن الناتج الفعلي: 3 3 3
foreach (var a in actions) a();

// السبب: كل Lambda تأسر نفس المتغير i (لا نسخته)
// الحل: نُسخة محلية في كل تكرار
for (int i = 0; i < 3; i++)
{
    int captured = i;  // متغير جديد كل دورة
    actions.Add(() => Console.WriteLine(captured));
}

تذكّر: منذ C# 5، حلقة foreach أنشأت متغيراً جديداً لكل تكرار تلقائياً (فلا مشكلة فيها). لكن for لم تتغير — لا تزال تُأسر نفس المتغير. دائماً استخدم متغيراً محلياً داخل جسم for.

static Lambda (C# 9+)

منذ C# 9 يمكنك كتابة static قبل Lambda لتمنع أي إغلاق. المترجم سيرفض الكود إذا حاولت الوصول لمتغير خارجي. هذا يحسّن الأداء ويمنع الأخطاء الدقيقة:

C# — Static Lambda 
int factor = 10;

// ❌ لن يُترجم — static تمنع الوصول إلى factor
Func<int, int> bad = static x => x * factor;

// ✅ مقبول — لا يستخدم أي متغير خارجي
Func<int, int> good = static x => x * 2;

شجرة التعبير — Expression Trees EXPRESSION<T> VS FUNC<T>

هناك فرق دقيق وحاسم بين Func<T> وExpression<Func<T>>. الأول كود قابل للتنفيذ (IL). الثاني شجرة بيانات تصف الكود — يمكن فحصها، تحليلها، وحتى ترجمتها إلى SQL!

هذا الفرق هو ما يجعل Entity Framework Core قادراً على ترجمة Where(e => e.Age > 30) إلى جملة SQL: لأنه يستلم شجرة تعبير، لا دالة منفّذة.

المعيار Func<T> / Action<T> Expression<Func<T>>
ماذا يحمل؟ كود IL قابل للتنفيذ شجرة بيانات تصف الكود
قابل للفحص؟ لا نعم — عبر Body وParameters
قابل للترجمة لـ SQL؟ لا نعم — أساس EF Core و LINQ to SQL
الاستخدام الشائع LINQ to Objects، Threads EF Core، LINQ to SQL، قواعد البيانات
C# — Expression Tree Inspection 
using System.Linq.Expressions;

// Func: كود منفّذ مباشرة
Func<int, bool> func = x => x > 10;
Console.WriteLine(func(20)); // True

// Expression: شجرة قابلة للفحص
Expression<Func<int, bool>> expr = x => x > 10;

Console.WriteLine(expr.Body);              // (x > 10)
Console.WriteLine(expr.Body.NodeType);     // GreaterThan
Console.WriteLine(expr.Parameters[0].Name);// x

// تحويله إلى Func قابل للتنفيذ
var compiled = expr.Compile();
Console.WriteLine(compiled(5)); // False

فخ شائع مع EF Core: استدعاء دالة عادية داخل Lambda محوّلة إلى Expression (مثلاً .Where(x => MyHelper(x))) قد يفشل — لأن EF Core لا يستطيع ترجمة MyHelper إلى SQL. اختبر دائماً أن استعلامك قابل للترجمة قبل النشر.

متى تستخدم أيهما؟

  • في LINQ to Objects (قوائم، مصفوفات) → استخدم Func العادي مباشرة.
  • في EF Core وLINQ to SQL → سياق الاستعلام يتوقع Expression<Func<T>> تلقائياً — لا تحتاج كتابة النوع.
  • إذا كنت تبني مكتبة ORM أو محوّل استعلامات → تعامل مع Expression مباشرة.

أفضل الممارسات الاحترافية BEST PRACTICES

لكتابة Lambda نظيفة وآمنة وفعّالة، اتبع هذه الإرشادات:

  • فضّل الصيغة التعبيرية (سطر واحد) على الجسم الكتلي عندما يكون المنطق بسيطاً — أنظف وأسهل قراءة.
  • استخدم أسماء معاملات ذات معنى: user => user.IsActive أفضل من x => x.IsActive.
  • لا تُفرط في التعشيش: Lambda داخل Lambda داخل Lambda تُصبح غير مقروءة — استخرجها إلى دالة مسماة.
  • احذر الإغلاق في الحلقات: لا تأسر متغيرات for دون نسخة محلية — أو استخدم static Lambda حيث أمكن.
  • تجنب الآثار الجانبية (Side Effects) داخل Lambda: لا تعدّل متغيرات خارجية داخل Select أو Where — يُنتج سلوكاً غير متوقع مع التنفيذ المؤجّل.
  • في EF Core: تحقق أن Lambda قابلة للترجمة — تجنب استدعاء دوال C# مخصصة داخل الاستعلام مباشرة.

الخلاصة والاختبار السريع SUMMARY & QUIZ

ما تعلمته في هذا الدرس

  • تعبير Lambda هو صيغة مختصرة لتعريف دالة مجهولة تُترجم إلى مفوضية أو شجرة تعبير.
  • أربعة أشكال للكتابة: بدون معاملات، معامل واحد، معاملات متعددة، جسم كتلي.
  • الإغلاقات (Closures) — Lambda تأسر المتغير الخارجي (المرجع، لا النسخة)، وكيف تتجنب فخ الحلقات.
  • الفرق بين Func وExpression<Func>، ودورها في EF Core.
  • ميزة static Lambda (C# 9) لمنع الإغلاق غير المقصود.
