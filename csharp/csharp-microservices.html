بناء Microservices بـ .NET

تقسيم النظام الضخم إلى خدمات صغيرة مستقلة، كل منها يعمل ويُنشر منفصلاً. ستتعلم المعمارية، Docker، API Gateway، gRPC، وأفضل الممارسات — مع مخطط تفاعلي يريك كيف تتواصل الخدمات.

1

ما هي Microservices؟

Microservices هو نمط معماري يقسّم التطبيق إلى خدمات صغيرة مستقلة، كل واحدة:

  • تعمل في عملية (process) منفصلة.
  • تنشر بشكل مستقل عن البقية.
  • تملك قاعدة بياناتها الخاصة.
  • تتواصل مع الأخرى عبر شبكة (HTTP/gRPC/Message).
  • تنظّم حول قدرة أعمال (Business Capability).

مثال: متجر إلكتروني

User Service

إدارة الحسابات، المصادقة، الملف الشخصي.

Product Service

الكتالوج، الفئات، المخزون.

Order Service

الطلبات، الدفع، الفواتير.

Notification Service

إرسال إيميلات وإشعارات.

الفكرة الأساسية

كل خدمة يمكن أن تكون صغيرة ويركّز فريقها عليها فقط. لو تعطّلت خدمة الإشعارات، لا يتوقف المتجر عن العمل — الطلبات تستمر.

2

Monolith مقابل Microservices

Microservices ليست دائماً الخيار الأفضل. لكل نمط نقاط قوة وضعف.

Monolith (متجانس)

  • ✅ بسيط للتطوير في البداية.
  • ✅ نشر واحد.
  • ✅ أداء أفضل بين المكونات.
  • ❌ تطوير أبطأ كلما كبر.
  • ❌ نشر صغير يعيد نشر كل شيء.
  • ❌ تقنية واحدة للكل.
التطبيق الكامل
Users Orders Products Notif

Microservices

  • ✅ فِرق مستقلة.
  • ✅ نشر مستقل لكل خدمة.
  • ✅ مرونة في التقنيات.
  • ✅ تحمّل الأعطال.
  • ❌ تعقيد تشغيلي كبير.
  • ❌ تأخير في الشبكة.
خدمات مستقلة
Users Orders Products Notif

جدول مقارنة

المعيار Monolith Microservices
البساطة عالية منخفضة
النشر موحّد مستقل
الأداء ممتاز تأخير شبكة
الفريق مركزي موزّع
التوسع عمودي أفقي
التعقيد منخفض مرتفع

لا تبدأ بـ Microservices

ابدأ بـ Monolith نظيف. إذا كبر المشروع واحتجت، انتقل تدريجياً إلى Microservices. هذا ما يسمى Monolith First — نهج Martin Fowler الموصى به.

3

بناء أول خدمة

كل خدمة هي مشروع ASP.NET Core Web API مستقل. لننشئ خدمة المنتجات.

Terminal
# إنشاء الحل الرئيسي
dotnet new sln -n EShop

# إنشاء 3 خدمات
dotnet new webapi -n ProductService
dotnet new webapi -n OrderService
dotnet new webapi -n UserService

# إضافتها للحل
dotnet sln add ProductService/ProductService.csproj
dotnet sln add OrderService/OrderService.csproj
dotnet sln add UserService/UserService.csproj

خدمة المنتجات

ProductService/Controllers/ProductsController.cs
using Microsoft.AspNetCore.Mvc;

namespace ProductService.Controllers;

[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    private readonly IProductService _service;

    public ProductsController(IProductService service)
        => _service = service;

    [HttpGet]
    public async Task<IEnumerable<ProductDto>> GetAll()
        => await _service.GetAllAsync();

    [HttpGet("{id:int}")]
    public async Task<ActionResult<ProductDto>> GetById(int id)
    {
        var product = await _service.GetByIdAsync(id);
        return product is null ? NotFound() : Ok(product);
    }

    [HttpPost]
    public async Task<ActionResult<ProductDto>> Create(CreateProductDto dto)
    {
        var product = await _service.CreateAsync(dto);
        return CreatedAtAction(nameof(GetById),
            new { id = product.Id }, product);
    }
}

ملف Dockerfile (لتشغيل الخدمة في حاوية)

ProductService/Dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 8080

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY ["ProductService.csproj", "./"]
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=build /app/publish .
ENV ASPNETCORE_URLS=http://+:8080
ENTRYPOINT ["dotnet", "ProductService.dll"]

كل خدمة قاعدة بياناتها

User Service → UsersDB. Order Service → OrdersDB. Product Service → ProductsDB. لا تشارك قاعدة بيانات بين الخدمات.

4

Docker و Kubernetes

لا يمكن تشغيل Microservices يدوياً — تحتاج أتمتة. Docker لحزم الخدمات، Kubernetes لإدارتها.

Docker Compose — تشغيل كل الخدمات بأمر واحد

docker-compose.yml
version: '3.8'

services:
  users-db:
    image: postgres:16
    environment:
      POSTGRES_DB: usersdb
      POSTGRES_PASSWORD: secret
    volumes:
      - users-data:/var/lib/postgresql/data

  user-service:
    build: ./UserService
    environment:
      ConnectionStrings__Default: Host=users-db;Database=usersdb;Username=postgres;Password=secret
    depends_on:
      - users-db
    ports:
      - "5001:8080"

  product-service:
    build: ./ProductService
    environment:
      ConnectionStrings__Default: Host=products-db;Database=productsdb;Username=postgres;Password=secret
    depends_on:
      - products-db
    ports:
      - "5002:8080"

  order-service:
    build: ./OrderService
    environment:
      ConnectionStrings__Default: Host=orders-db;Database=ordersdb;Username=postgres;Password=secret
      Services__User__Url: http://user-service:8080
      Services__Product__Url: http://product-service:8080
    depends_on:
      - orders-db
      - user-service
      - product-service
    ports:
      - "5003:8080"

  api-gateway:
    image: nginx:alpine
    volumes:
      - ./gateway.conf:/etc/nginx/nginx.conf
    ports:
      - "8080:80"
    depends_on:
      - user-service
      - product-service
      - order-service

volumes:
  users-data:
  products-data:
  orders-data:

أمر واحد لتشغيل الكل

Terminal
# تشغيل كل الخدمات في الخلفية
docker compose up -d

# مشاهدة اللوجات
docker compose logs -f user-service

# إيقاف الكل
docker compose down

# حذف كل شيء (بما فيه البيانات)
docker compose down -v

Kubernetes — للإنتاج

عندما ينمو المشروع، انتقل من Docker Compose إلى Kubernetes:

الميزة Docker Compose Kubernetes
الاستخدام التطوير المحلي الإنتاج
Auto-scaling لا نعم
Self-healing محدود كامل
Load Balancing يدوي مدمج
Rolling Updates لا نعم

6

التواصل: REST و gRPC

الخدمات تتحدث مع بعضها بطريقتين رئيسيتين: REST/HTTP (متزامن) و Message Broker (غير متزامن).

الطريقة 1: HTTP Client

OrderService — استدعاء ProductService
public class ProductClient
{
    private readonly HttpClient _http;

    public ProductClient(HttpClient http) => _http = http;

    public async Task<ProductDto?> GetAsync(int id)
    {
        var response = await _http.GetAsync($"/api/products/{id}");
        if (!response.IsSuccessStatusCode) return null;

        return await response.Content
            .ReadFromJsonAsync<ProductDto>();
    }
}

// التسجيل في DI
builder.Services.AddHttpClient<ProductClient>(c =>
{
    c.BaseAddress = new Uri(
        builder.Configuration["Services:Product:Url"]!);
});

الطريقة 2: gRPC

gRPC هو بديل حديث لـ REST — أسرع، يستخدم Protocol Buffers، يدعم Streaming.

Protos/product.proto
syntax = "proto3";

package product;

service ProductService {
  rpc GetProduct (GetProductRequest) returns (ProductReply);
  rpc ListProducts (Empty) returns (stream ProductReply);
}

message GetProductRequest {
  int32 id = 1;
}

message ProductReply {
  int32 id = 1;
  string name = 2;
  double price = 3;
}

مقارنة REST و gRPC

المعيار REST/JSON gRPC
الأداء جيد ممتاز
حجم البيانات JSON نصي Binary
سهولة الاستخدام بسيط يحتاج proto
Streaming محدود كامل
دعم المتصفح كامل يحتاج gRPC-Web

متى تستخدم أيهما؟

REST للتواصل مع العملاء (Browsers/Mobile). gRPC للتواصل بين الخدمات الداخلية (أسرع بكثير).

7

API Gateway

بدلاً من أن يتصل العميل بخدمات متعددة، يتصل بـ Gateway واحد يوجّه الطلبات ويعالج القضايا الشاملة (Cross-cutting Concerns).

ماذا يفعل API Gateway؟

Routing

يوجّه /api/users إلى UserService وهكذا.

Authentication

يتحقق من JWT قبل تمرير الطلب.

Rate Limiting

يحمي الخدمات من الطلبات الزائدة.

Logging

يسجل كل طلب في مكان واحد.

Load Balancing

يوزع الطلبات على نسخ الخدمة.

Retry & Circuit Breaker

يعيد المحاولة أو يعزل خدمة فاشلة.

مثال: Ocelot

ocelot.json
{
  "Routes": [
    {
      "UpstreamPathTemplate": "/api/users/{everything}",
      "UpstreamHttpMethod": [ "GET", "POST", "PUT" ],
      "DownstreamPathTemplate": "/api/users/{everything}",
      "DownstreamScheme": "http",
      "DownstreamHostAndPorts": [
        { "Host": "user-service", "Port": 8080 }
      ]
    },
    {
      "UpstreamPathTemplate": "/api/products/{everything}",
      "UpstreamHttpMethod": [ "GET", "POST" ],
      "DownstreamPathTemplate": "/api/products/{everything}",
      "DownstreamScheme": "http",
      "DownstreamHostAndPorts": [
        { "Host": "product-service", "Port": 8080 }
      ]
    }
  ]
}

Gateway = نقطة فشل واحدة

لأن كل الطلبات تمر عبره، Gateway قد يكون عنق زجاجة. شغّله في وضع HA (نسخ متعددة) وراقب أداءه دائماً.

8

Message Broker — التواصل غير المتزامن

بدلاً من انتظار رد فوري، ترسل الخدمة حدثاً لـ Broker، والخدمات الأخرى تستمع وتتفاعل. هذا هو نمط Event-Driven.

مثال: إرسال إشعار عند إنشاء طلب

OrderService — نشر حدث
public async Task PlaceOrderAsync(Order order)
{
    // 1) حفظ الطلب في قاعدة البيانات
    await _db.Orders.AddAsync(order);
    await _db.SaveChangesAsync();

    // 2) نشر حدث — لا ننتظر أحداً
    await _messageBus.PublishAsync(
        new OrderPlacedEvent
        {
            OrderId = order.Id,
            UserEmail = order.UserEmail,
            Total = order.Total
        });
}
NotificationService — استقبال الحدث
public class OrderPlacedHandler
    : IIntegrationEventHandler<OrderPlacedEvent>
{
    private readonly IEmailSender _email;

    public OrderPlacedHandler(IEmailSender email) => _email = email;

    public async Task HandleAsync(OrderPlacedEvent evt)
    {
        await _email.SendAsync(
            evt.UserEmail,
            "تم تأكيد طلبك",
            $"رقم الطلب: {evt.OrderId}");
    }
}

لماذا Message Broker؟

فصل تام: OrderService لا يعرف من يستمع للأحداث. تحمّل الأعطال: لو تعطّلت NotificationService، تُحفظ الأحداث وتُعالج عند عودتها.

9

أفضل الممارسات

  • ابدأ بـ Monolith: لا تنتقل إلى Microservices إلا عند الحاجة الحقيقية.
  • خدمة = منطق أعمال كامل: لا تقسم بناءً على طبقات تقنية (Users, Orders) بل على قدرات (Billing, Shipping).
  • قاعدة بيانات لكل خدمة: لا تشارك قاعدة بيانات بين خدمتين.
  • API Gateway نقطة واحدة: لا تعرّض الخدمات مباشرة للعملاء.
  • Async للتواصل: استخدم Message Broker بين الخدمات، وتجنب Calls المتزامنة الطويلة.
  • Retry + Circuit Breaker: عالج فشل الخدمات البعيدة تلقائياً (Polly).
  • رصد مركزي: Logs وTraces وMetrics في مكان واحد (ELK/OpenTelemetry).
  • Distributed Tracing: تتبع طلب واحد عبر كل الخدمات بـ Correlation ID.
  • Saga Pattern: للعمليات الموزعة التي تحتاج Rollback.
  • CI/CD لكل خدمة: كل خدمة لها pipeline خاص للنشر.
  • Docker دائماً: لا تنشر خدمة بدون حاوية.
  • لا تُفرط في التقسيم: 50 خدمة صغيرة قد تكون أسوأ من 5 كبيرة.

الحقيقة الصادقة

Microservices تحل مشاكل تنظيمية أكثر من تقنية. إذا كان لديك فريق واحد صغير ومشروع بسيط، Monolith قد يكون أفضل. اختر ما يخدم مشروعك — لا ما يقول الترند.
