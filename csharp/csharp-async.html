لماذا نحتاج تعدد المسارات؟ WHY MULTI-THREADING?

تخيل أنك تبني تطبيق سطح مكتب يقوم بتحليل آلاف الملفات أو تحميل بيانات من الإنترنت. في البرمجة التقليدية (Single-Threaded)، ينفّذ التطبيق التعليمات واحدة تلو الأخرى، وطالما انشغل الخيط الرئيسي (Main Thread) بعملية طويلة، فإن واجهة المستخدم تتجمد ولا تستجيب للنقر أو الكتابة. هذه المشكلة تحديداً هي ما جعلت البرمجة غير المتزامنة (Asynchronous Programming) ضرورة في كل منصة حديثة.

البرمجة متعددة المسارات تسمح للبرنامج بتنفيذ أكثر من مهمة في الوقت نفسه. بدلاً من أن يقوم الخيط الرئيسي بكل العمل، نُفوّض المهام الثقيلة إلى خيوط خلفية (Background Threads)، فيبقى الخيط الرئيسي حراً للتفاعل مع المستخدم. والمحصلة: تطبيق سريع، متجاوب، وقادر على استغلال أنوية المعالج المتعددة.

القاعدة الذهبية في هندسة البرمجيات: أي عملية قد تستغرق أكثر من 50 مللي ثانية يجب ألا تُنفّذ على خيط واجهة المستخدم. حوّلها إلى عملية غير متزامنة أو نفّذها في الخلفية.

المفاهيم الأساسية في .NET CORE CONCEPTS

في C# الحديثة لم نعد نتعامل مباشرة مع فئة Thread القديمة في معظم السيناريوهات. بدلاً من ذلك نعتمد على نموذج Task-based Asynchronous Pattern (TAP) الذي يقوم على Task وasync/await. فهم هذه المكونات الأربعة هو مفتاح إتقان الموضوع:

Thread

خيط تنفيذ منخفض المستوى. ثقيل في الإنشاء والإدارة (1MB stack افتراضياً). نادراً ما يُستخدم مباشرة في الكود الحديث.

Task

تجريد عالي المستوى يمثّل عملية غير متزامنة. يديره ThreadPool تلقائياً، ويدعم الإلغاء والانتظار والتجميع.

async / await

كلمات مفتاحية تحوّل الكود إلى آلة حالة (State Machine) تلقائياً، فتبدو العمليات غير المتزامنة كأنها متزامنة القراءة.

ThreadPool

مجمّع خيوط يديره الـ Runtime لإعادة استخدام الخيوط بدلاً من إنشاء خيط جديد لكل مهمة، مما يرفع الأداء.

تحذير هام: لا تستخدم Thread.Abort() أبداً في .NET الحديثة. فهي غير مدعومة على Linux/macOS وقد تسبب سلوكاً غير متوقع وحتى فساداً في الذاكرة. الإلغاء الصحيح يكون تعاونياً عبر CancellationToken.

Thread مقابل Task — أيهما تختار؟ THREAD VS TASK

كثير من المبتدئين يسألون: "لماذا لا أستخدم Thread مباشرة؟". الجواب في هذا الجدول المقارن. لاحظ أن Task ليس بديلاً "أسرع" فحسب، بل هو تجريد أعلى يخفيك من إدارة الخيوط المعقدة:

المعيار Thread Task
المستوى منخفض (OS-Level) عالي (Runtime-managed)
كلفة الإنشاء عالية (~1MB stack + syscall) منخفضة (تُدار عبر ThreadPool)
دعم await لا نعم (أساس async/await)
الإلغاء Abort (خطر) أو تعاوني CancellationToken أصيل
الاستخدام المفضل سيناريوهات نادرة جداً (خيط دائم، STA) الافتراضي لكل شيء تقريباً

مثال على إنشاء مهمة وحساب ناتجها بدون تجميد:

C# 
using System;
using System.Threading.Tasks;

public class Calculator
{
    public static long SumRange(int from, int to)
    {
        long total = 0;
        for (int i = from; i < to; i++)
            total += i;
        return total;
    }
}

public class Program
{
    public static async Task Main()
    {
        Console.WriteLine("بدأ الحساب...");

        // Task.Run ينقل العمل إلى ThreadPool
        Task<long> t = Task.Run(() => Calculator.SumRange(0, 100_000_000));

        // await يحرر الخيط الحالي حتى تنتهي المهمة
        long result = await t;

        Console.WriteLine($"النتيجة: {result}");
    }
}

ملاحظة: Task.Run مخصّص للعمليات المعتمدة على المعالج (CPU-Bound) مثل الحسابات. أما عمليات الشبكة وقواعد البيانات فلها دوال غير متزامنة جاهزة (مثل GetStringAsync) — لا تلفّها بـ Task.Run أبداً.

آلية async / await بالتفصيل HOW ASYNC/AWAIT WORKS

عند كتابة await، لا يحدث "خيط جديد" كما يظن البعض. ما يحدث فعلياً أن المترجم يحوّل الدالة إلى آلة حالة (State Machine). عند الوصول إلى await على مهمة لم تكتمل بعد، تُسجَّل نقطة الاستئناف وتُعاد السيطرة إلى المتصل فوراً. وعندما تكتمل المهمة، يستأنف التنفيذ تلقائياً من حيث توقف.

هذا الفرق جوهري بين الحجب (Blocking) والانتظار غير المحجوب:

C# — Blocking vs Non-Blocking 
using System.Net.Http;
using System.Threading.Tasks;

public class DataFetcher
{
    private static readonly HttpClient client = new HttpClient();

    // ❌ سيئ: نحجب الخيط الرئيسي حتى تنتهي الشبكة
    public static string FetchBlocking(string url)
    {
        return client.GetStringAsync(url).Result; // Deadlock محتمل!
    }

    // ✅ ممتاز: await يحرر الخيط فوراً
    public static async Task<string> FetchAsync(string url)
    {
        string data = await client.GetStringAsync(url);
        return data;
    }
}

فخ الـ Deadlock الشهير: استدعاء .Result أو .Wait() على مهمة غير متزامنة داخل سياق متزامن (مثل WinForms أو ASP.NET) يؤدي إلى طريق مسدود. القاعدة: لا تخلط بين العالم المتزامن وغير المتزامن — "Async all the way".

وهذا هو الكود الحقيقي الذي يحاكي المختبر — لاحظ الفرق بين النسختين:

C# — Race Condition vs Lock 
using System;
using System.Threading;
using System.Threading.Tasks;

class Counter
{
    private int _value;
    private readonly object _gate = new object();

    // ❌ عرضة للتسابق: increment ليس عملية ذرية
    public void IncrementUnsafe() => _value++;

    // ✅ آمن: قفل يضمن تنفيذ خيط واحد في كل مرة
    public void IncrementSafe()
    {
        lock (_gate) { _value++; }
    }

    public int Value => _value;
}

class Program
{
    static async Task Main()
    {
        var counter = new Counter();

        // مهمتان متوازيتان — كل واحدة تزيد 10,000 مرة
        Task t1 = Task.Run(() => { for (int i = 0; i < 10_000; i++) counter.IncrementUnsafe(); });
        Task t2 = Task.Run(() => { for (int i = 0; i < 10_000; i++) counter.IncrementUnsafe(); });

        await Task.WhenAll(t1, t2);

        Console.WriteLine($"النتيجة المتوقعة: 20000 | الفعلية: {counter.Value}");
        // غالباً ستحصل على رقم أقل — فقدت تحديثات بسبب التسابق
    }
}

البدائل الحديثة للتزامن: إلى جانب lock، توجد أدوات أفضل حسب الحالة: Interlocked للعمليات الذرية البسيطة، SemaphoreSlim للتحكم في عدد المتصلين، ConcurrentDictionary وConcurrentBag للمجموعات الآمنة، وChannel<T> للاتصال بين المنتج والمستهلك.

أفضل الممارسات الاحترافية BEST PRACTICES

لكتابة كود متعدد المسارات آمن وقابل للصيانة، اتبع هذه الإرشادات المستخلصة من تجارب فرق الإنتاج الكبرى:

  • لا تستخدم async void إلا في معالجات الأحداث. استخدم دائماً async Task، لأن الاستثناءات في async void لا يمكن التقاطها.
  • استخدم ConfigureAwait(false) داخل المكتبات. يمنع العودة غير الضرورية إلى سياق الخيط الأصلي ويحسّن الأداء ويتجنب Deadlocks.
  • مرّر CancellationToken في كل دالة غير متزامنة طويلة. الإلغاء التعاوني ضروري لتجربة مستخدم جيدة وتحرير الموارد.
  • لا تلفّ عمليات I/O في Task.Run. استخدم الدوال غير المتزامنة الجاهزة مباشرة — فهي لا تحجب الخيط أصلاً.
  • استخدم Task.WhenAll بدلاً من حلقة await. إذا كانت المهام مستقلة، شغّلها معاً ثم انتظر انتهاءها دفعة واحدة.
  • فضّل الأنواع الآمنة للخيوط. مثل ConcurrentDictionary، ImmutableList، وChannel<T> بدل القفل اليدوي كلما أمكن.

الخلاصة والاختبار السريع SUMMARY & QUIZ

ما تعلمته في هذا الدرس

  • الفرق بين التنفيذ المتزامن وغير المتزامن وأثر ذلك على استجابة الواجهة.
  • متى تستخدم Task.Run (عمليات المعالج) ومتى تستخدم await على دوال I/O.
  • لماذا async void و.Result خطران، وكيف تتجنب Deadlock.
  • ماهية حالات التسابق (Race Conditions) وطرق حمايتها بـlock وInterlocked.
