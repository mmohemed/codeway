1

ما هي هندسة البرمجيات؟

هندسة البرمجيات (Software Engineering) هي التخصص الذي يطبّق المبادئ الهندسية على تطوير البرمجيات. هدفها بناء أنظمة موثوقة، قابلة للصيانة، وقابلة للتوسع — وليس فقط كود يعمل.

عالمياً، تُعرّف IEEE هندسة البرمجيات بأنها: "تطبيق منهجي، منضبط، وقابل للقياس لمنهجية التطوير والتشغيل والصيانة للبرمجيات."

لماذا نحتاجها؟

لأن البرمجيات تفشل. الدراسات تُظهر أن نسبة كبيرة من المشاريع البرمجية تتأخر أو تتجاوز ميزانيتها أو تُلغى. السبب غالباً ليس الكود نفسه، بل سوء التخطيط والتصميم.

مشكلة "الكود الشغّال فقط"

الكود الذي يعمل اليوم قد يصبح كابوساً غداً إن لم يُصمم جيداً.

العمل الجماعي

في الفريق، الكود يُقرأ أكثر مما يُكتب — لذا يجب أن يكون واضحاً.

التغيّر حتمي

المتطلبات تتغير، والمكتبات تتحدث، والتقنيات تتطور — التصميم الجيد يتحمل ذلك.

الأمان والموثوقية

تطبيقات البنوك والصحة لا تحتمل الأخطاء — الهندسة تضمن الجودة.

فكرة محورية

هندسة البرمجيات لا تعني "كتابة كود أكثر تعقيداً"، بل تعني كتابة كود أبسط، أوضح، وأكثر قابلية للتغيير. التعقيد عدوّك، والوضوح هو هدفك.

2

الفرق بين البرمجة والهندسة

البرمجة مهارة، وهندسة البرمجيات مهنة. الفرق يشبه الفرق بين النجارة وبناء منزل: كليهما يحتاج أدوات، لكن بناء المنزل يحتاج مخططاً وأساساً وأماناً.

البرمجة (Coding)

  • التركيز: كتابة كود يعمل.
  • الأفق: الملف أو الدالة الحالية.
  • النجاح: "هل يعمل الآن؟"
  • الوقت: أيام أو أسابيع.
  • الأدوات: محرر كود + مترجم.

الهندسة (Engineering)

  • التركيز: نظام كامل يحل مشكلة.
  • الأفق: السنة أو أكثر.
  • النجاح: "هل سيصمد بعد سنة؟"
  • الوقت: أشهر أو سنوات.
  • الأدوات: Git, CI/CD, Tests, DI...

مثال على الفرق في C#

لنفترض أنك تريد دالة تحسب خصماً على سعر. البرمجة السريعة تكتبها في سطر واحد. الهندسة تسأل: هل الخصم ثابت؟ هل يتغير؟ كيف سنختبره؟

برمجة سريعة ❌
public double GetPrice(double price)
{
    return price * 0.9; // خصم 10% مضمّن
}
هندسة برمجيات ✅
public interface IDiscountStrategy
{
    double Apply(double price);
}

public class PercentageDiscount : IDiscountStrategy
{
    private readonly double _rate;
    public PercentageDiscount(double rate) => _rate = rate;
    public double Apply(double price) => price * (1 - _rate);
}

public class FixedDiscount : IDiscountStrategy
{
    private readonly double _amount;
    public FixedDiscount(double amount) => _amount = amount;
    public double Apply(double price) => Math.Max(0, price - _amount);
}

الكود الثاني أطول، لكنه قابل للاختبار، للتوسيع، وللتغيير دون المساس بباقي النظام. هذا هو جوهر هندسة البرمجيات.

3

دورة حياة تطوير البرمجيات (SDLC)

SDLC (Software Development Life Cycle) هي المراحل التي يمر بها أي مشروع برمجي احترافي من الفكرة إلى الصيانة.

1
التخطيط

ما المشكلة؟ من المستخدم؟

2
التحليل

المتطلبات الوظيفية وغير الوظيفية.

3
التصميم

المعمارية، الفئات، قاعدة البيانات.

4
التنفيذ

كتابة الكود، الاختبارات، المراجعة.

5
الاختبار

التحقق من الجودة والأمان.

6
الصيانة

إصلاح الأخطاء، تحسين، إضافة ميزات.

أنماط SDLC

النمط الوصف مناسب لـ
Waterfall مراحل متتالية لا رجوع فيها مشاريع ذات متطلبات ثابتة
Agile دورات قصيرة (Sprints) + تعاون مستمر مشاريع متغيرة أو غير واضحة
Scrum إطار Agile بأدوار محددة (PO, SM, Team) فرق تطوير منتجات
DevOps دمج التطوير والتشغيل + أتمتة أنظمة تحتاج نشراً سريعاً

لا يوجد نمط "أفضل"

اختيار النمط يعتمد على طبيعة المشروع وحجم الفريق والمخاطر. معظم الشركات الحديثة تستخدم Agile + DevOps.

4

لماذا C# في هندسة البرمجيات؟

C# هي واحدة من أفضل اللغات لتعلّم هندسة البرمجيات لأنها تجمع بين بساطة القراءة، قوة النظام البيئي (.NET)، والدعم الكامل للمبادئ الهندسية الحديثة.

مزايا C# لمهندس البرمجيات

  • النظام البيئي .NET: مكتبات ضخمة، DI مدمج، Entity Framework، ASP.NET Core.
  • البرمجة الكائنية الكاملة: وراثة، واجهات، تجريد — مفاهيم أساسية في التصميم.
  • دعم Async/Await: برمجة غير متزامنة بأسلوب أنيق.
  • الاختبار: xUnit, NUnit, Moq — دعم ممتاز لـ TDD.
  • التوافق العابر: Windows, Linux, macOS, WebAssembly.
  • أدوات ممتازة: Visual Studio, Rider, VS Code.

عمارة نموذجية بـ C#

النظام الاحترافي في .NET يُبنى عادة على طبقات واضحة. إليك نموذجاً شائعاً:

طبقات تطبيق .NET احترافي
Presentation Layer Web / WPF / API
Application Layer Use Cases / Services
Domain Layer Entities / Rules
Infrastructure Layer DB / Files / External APIs

هذا الفصل يسمح بتبديل قاعدة البيانات دون تغيير منطق الأعمال، أو إضافة واجهة جديدة (Web أو Mobile) دون إعادة كتابة النظام. هذا هو جوهر "Clean Architecture".

قاعدة التبعية

في المعمارية النظيفة: التبعيات تتجه دائماً نحو المركز (Domain). الطبقات الخارجية تعتمد على الداخلية، وليس العكس.

5

مبادئ التصميم الجيد

مبادئ SOLID هي الأساس الذي تُبنى عليه البرمجيات النظيفة. سنمر عليها سريعاً هنا، مع تطبيق C# لكل مبدأ.

1. S — مبدأ المسؤولية الواحدة (SRP)

كل فئة يجب أن يكون لها سبب واحد فقط للتغيير.

SRP
// ❌ فئة تفعل 3 أشياء
public class UserService
{
    public void Register(User user) { /* ... */ }
    public void SendEmail(string email) { /* ... */ }
    public void Log(string message) { /* ... */ }
}

// ✅ كل فئة لها مسؤولية واحدة
public class UserService { public void Register(User u) { } }
public class EmailService { public void Send(string e) { } }
public class Logger { public void Log(string m) { } }

2. O — مبدأ الانفتاح/الانغلاق (OCP)

الفئات مفتوحة للتوسيع، مغلقة للتعديل.

OCP
public abstract class Shape
{
    public abstract double Area();
}

public class Circle : Shape
{
    public double Radius { get; set; }
    public override double Area() => Math.PI * Radius * Radius;
}

public class Rectangle : Shape
{
    public double Width { get; set; }
    public double Height { get; set; }
    public override double Area() => Width * Height;
}

// إضافة شكل جديد لا تتطلب تعديل الكود القديم

3. L — مبدأ استبدال ليسكوف (LSP)

كائنات الفئة الفرعية يجب أن تحل محل كائنات الفئة الأم دون كسر السلوك.

LSP
// ❌ انتهاك: Square لا يمكن أن يحل محل Rectangle
public class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
}

public class Square : Rectangle
{
    public override int Width { set { base.Width = value; base.Height = value; } }
}

// ✅ الحل: تجريد أفضل
public abstract class Shape { public abstract int Area(); }
public class Rectangle : Shape { /* ... */ }
public class Square : Shape { /* ... */ }

4. I — مبدأ فصل الواجهات (ISP)

لا تُجبر العملاء على الاعتماد على واجهات لا يستخدمونها.

5. D — مبدأ عكس التبعية (DIP)

اعتمد على التجريد، لا على التنفيذ.

DIP + DI
public interface IEmailSender
{
    Task SendAsync(string to, string body);
}

public class SmtpEmailSender : IEmailSender
{
    public async Task SendAsync(string to, string body) { /* ... */ }
}

public class OrderService
{
    private readonly IEmailSender _mailer;
    public OrderService(IEmailSender mailer) => _mailer = mailer;

    public async Task PlaceOrderAsync()
    {
        // منطق الطلب
        await _mailer.SendAsync("user@example.com", "تم طلبك");
    }
}

// في Program.cs
builder.Services.AddScoped<IEmailSender, SmtpEmailSender>();
builder.Services.AddScoped<OrderService>();

النتيجة

يمكنك تبديل SmtpEmailSender بـ SendGridEmailSender دون تعديل OrderService — فقط سطر في DI.

6

تطبيق عملي: قبل وبعد

لنرَ كيف يتحول كود بسيط إلى كود احترافي عبر التطبيق التدريجي لمبادئ الهندسة.

المرحلة 1: الكود المبدئي (يعمل فقط)

❌ قبل
public class Order
{
    public void Save()
    {
        // 1) اتصال قاعدة البيانات
        var conn = new SqlConnection("Server=...");
        conn.Open();
        var cmd = new SqlCommand("INSERT INTO Orders ...", conn);
        cmd.ExecuteNonQuery();

        // 2) إرسال إيميل
        var smtp = new SmtpClient("smtp.example.com");
        smtp.Send("a@b.com", "c@d.com", "تم الطلب", "...");

        // 3) تسجيل
        File.AppendAllText("log.txt", "order saved");
    }
}

المشاكل:

  • الكلاس يعرف كل تفاصيل البنية التحتية (DB, SMTP, Files).
  • لا يمكن اختباره بدون قاعدة بيانات حقيقية.
  • تغيير مزوّد الإيميل يتطلب تعديل الكود.
  • لا يوجد معالجة أخطاء أو Async.

المرحلة 2: الفصل والاعتماد على التجريد

✅ بعد
// 1) الكيانات
public class Order
{
    public int Id { get; set; }
    public string CustomerEmail { get; set; } = "";
    public decimal Total { get; set; }
}

// 2) الواجهات (التجريد)
public interface IOrderRepository
{
    Task AddAsync(Order order);
}

public interface IEmailSender
{
    Task SendAsync(string to, string body);
}

public interface ILogger
{
    void Info(string message);
}

// 3) التطبيق
public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly IEmailSender _mailer;
    private readonly ILogger _log;

    public OrderService(
        IOrderRepository repo,
        IEmailSender mailer,
        ILogger log)
    {
        _repo = repo;
        _mailer = mailer;
        _log = log;
    }

    public async Task PlaceAsync(Order order)
    {
        await _repo.AddAsync(order);
        await _mailer.SendAsync(order.CustomerEmail, "تم طلبك");
        _log.Info($"تم طلب #{order.Id}");
    }
}

// 4) التسجيل في DI
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddScoped<IEmailSender, SmtpEmailSender>();
builder.Services.AddScoped<ILogger, FileLogger>();
builder.Services.AddScoped<OrderService>();
الخاصية قبل بعد
الاختبار صعب سهل (Mocks)
قابلية التبديل تعديل الكود سطر DI
المسؤولية مشتركة واحدة
الأداء متزامن Async

الدرس المستفاد

الهندسة ليست إضافة طبقات بلا داعٍ — بل هي وضع كل مسؤولية في مكانها الصحيح. النتيجة: كود أبسط للفهم، وأسهل للتغيير، وأقوى في الإنتاج.

7

أدوات المهندس

المهندس لا يعمل بالكود وحده. هناك أدوات وممارسات تحيط دورة التطوير وتضمن الجودة.

Git & GitHub

إدارة الإصدارات والتعاون — أساس أي مشروع.

Unit Testing

xUnit, NUnit, Moq — لضمان عدم كسر الكود.

CI/CD

GitHub Actions, Azure DevOps — أتمتة البناء والنشر.

Static Analysis

SonarQube, Roslyn Analyzers — اكتشاف المشاكل مبكراً.

Monitoring

Application Insights, Serilog — مراقبة الأداء في الإنتاج.

Docker

حزم التطبيق ليعمل في أي بيئة بشكل موحد.

سطر أوامر سريع

Terminal
# إنشاء مشروع وحل واحد
dotnet new sln -n MySolution
dotnet new console -n MyApp
dotnet sln add MyApp/MyApp.csproj

# إنشاء مشروع اختبار
dotnet new xunit -n MyApp.Tests
dotnet sln add MyApp.Tests/MyApp.Tests.csproj
dotnet add MyApp.Tests reference MyApp

# بناء وتشغيل الاختبارات
dotnet build
dotnet test

لماذا CLI؟

سطر الأوامر أسرع، ويعمل في أي بيئة (Linux/macOS/Windows)، ويُستخدم في أنظمة CI/CD — لذا إتقانه ضروري لكل مهندس.

8

مسارك القادم

هذا الدرس كان تمهيداً. الدروس القادمة في هذا القسم ستأخذك خطوة بخطوة إلى الأمام.

  • SOLID Deep Dive: تطبيق تفصيلي لكل مبدأ مع تمارين.
  • Design Patterns: Singleton, Factory, Repository, Decorator...
  • Clean Code: تسمية، تنظيم، تعليقات، تحسين.
  • Unit Testing: xUnit + Moq + TDD.
  • ASP.NET Core: بناء APIs احترافية.
  • Entity Framework: ORM وقواعد البيانات.
  • Microservices: تقسيم النظام لخدمات مستقلة.

نصيحة ذهبية

لا تحاول تعلّم كل شيء دفعة واحدة. اختر مبدأً واحداً، طبّقه على مشروعك الحالي، ثم انتقل للتالي. الممارسة أهم من النظرية.
