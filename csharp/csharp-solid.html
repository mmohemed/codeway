ما هي SOLID؟

SOLID هي خمسة مبادئ في تصميم البرمجيات كائنية التوجه، صاغها Robert C. Martin (Uncle Bob). هدفها جعل الكود قابلاً للفهم، للتوسيع، وللصيانة.

لماذا هذه المبادئ مهمة؟

لأن البرمجيات تتغير باستمرار. متطلبات تتغير، مكتبات تتحدث، ميزات تُضاف. الكود الذي لا يلتزم بهذه المبادئ يصبح هشاً وصعب التعديل — وتزيد فيه الأخطاء بشكل مضاعف.

مبدأ عام

SOLID ليست قواعد صارمة بل إرشادات. لكل قاعدة استثناءات. الهدف: كود أبسط للفهم وأسهل للتغيير — وليس مجرد "توافق شكلي" مع المبادئ.

2

المسؤولية الواحدة (SRP)

S
مبدأ المسؤولية الواحدة
Single Responsibility Principle
كل فئة يجب أن يكون لها سبب واحد فقط للتغيير. أي يجب أن تكون مسؤولة عن شيء واحد فقط.

مثال من الواقع

تخيل أن لديك كلاس UserService يقرأ المستخدم من قاعدة البيانات، يرسل له إيميل، ويسجل في الملف. لو تغيّرت قاعدة البيانات، أو مزوّد الإيميل، أو طريقة التسجيل — كلها تُجبرك على تعديل نفس الكلاس.

قبل — مسؤوليات متعددة

كلاس UserService يدير 3 أشياء: التخزين، الإيميل، التسجيل. أي تغيير في أي منها يكسر الكلاس، وأي اختبار يتطلب تحضير بيئة كاملة.

بعد — مسؤولية واحدة لكل كلاس

UserRepository (تخزين) + EmailService (إيميل) + Logger (تسجيل). كلها تُختبر منفصلة، وتُبدَّل منفصلة.

الكود قبل (❌)

SRP — قبل
public class UserService
{
    public void Register(User user)
    {
        // 1) حفظ في قاعدة البيانات
        var conn = new SqlConnection("...");
        conn.Open();
        new SqlCommand("INSERT INTO Users...", conn).ExecuteNonQuery();

        // 2) إرسال إيميل ترحيب
        var smtp = new SmtpClient("smtp.example.com");
        smtp.Send("noreply@site.com", user.Email,
                  "مرحباً", "تم إنشاء حسابك");

        // 3) تسجيل في ملف
        File.AppendAllText("log.txt", $"new user: {user.Email}");
    }
}

الكود بعد (✅)

SRP — بعد
public interface IUserRepository
{
    Task AddAsync(User user);
}

public interface IEmailService
{
    Task SendWelcomeAsync(string email);
}

public interface ILogger
{
    void Info(string message);
}

// كل فئة الآن مسؤولة عن شيء واحد فقط
public class UserService
{
    private readonly IUserRepository _repo;
    private readonly IEmailService _email;
    private readonly ILogger _log;

    public UserService(
        IUserRepository repo,
        IEmailService email,
        ILogger log)
    {
        _repo = repo;
        _email = email;
        _log = log;
    }

    public async Task RegisterAsync(User user)
    {
        await _repo.AddAsync(user);
        await _email.SendWelcomeAsync(user.Email);
        _log.Info($"مستخدم جديد: {user.Email}");
    }
}

كيف تعرف أنك تخالف SRP؟

اكتب وصفاً للكلاس. إن احتوى "و" في الوصف — مثل "يدير المستخدمين و يرسل إيميلات و يسجل" — فأنت تخالف SRP.

3

الانفتاح/الانغلاق (OCP)

O
مبدأ الانفتاح/الانغلاق
Open/Closed Principle
الفئات يجب أن تكون مفتوحة للتوسيع ومغلقة للتعديل. أي: يمكنك إضافة سلوك جديد دون تعديل الكود الموجود.

مثال: نظام خصومات

لديك متجر يطبق خصومات. في البداية يوجد خصم بسيط. لكن مع الوقت، تُضاف خصومات جديدة: موسمية، للعملاء الدائمين، إلخ. لو اعتمدت على if/switch — ستنمو الدالة بلا نهاية.

الكود قبل (❌)

OCP — قبل
public class DiscountCalculator
{
    public double Calculate(double price, string type)
    {
        if (type == "seasonal")
            return price * 0.7;

        if (type == "loyal")
            return price * 0.9;

        if (type == "coupon")
            return price - 50;

        // كل نوع جديد = تعديل هنا
        return price;
    }
}

الكود بعد (✅)

OCP — بعد
public interface IDiscountStrategy
{
    double Apply(double price);
}

public class SeasonalDiscount : IDiscountStrategy
{
    public double Apply(double p) => p * 0.7;
}

public class LoyalCustomerDiscount : IDiscountStrategy
{
    public double Apply(double p) => p * 0.9;
}

public class CouponDiscount : IDiscountStrategy
{
    public double Apply(double p) => Math.Max(0, p - 50);
}

public class DiscountCalculator
{
    public double Calculate(double price, IDiscountStrategy strategy)
        => strategy.Apply(price);
}

الآن: لإضافة خصم "عيد ميلاد"، ننشئ كلاساً جديداً فقط — دون تعديل الكود الموجود.

كيف تعرف أنك تخالف OCP؟

لو كان كل نوع جديد يُجبرك على تعديل switch أو if-else في نفس الكلاس — فأنت تخالف OCP.

4

استبدال ليسكوف (LSP)

L
مبدأ استبدال ليسكوف
Liskov Substitution Principle
كائنات الفئة الفرعية يجب أن تكون قابلة للاستبدال بكائنات الفئة الأم دون كسر سلوك البرنامج.

المثال الشهير: المربع والمستطيل

في الرياضيات، المربع هو مستطيل (له نفس الزوايا القائمة). لكن في البرمجة، جعل Square يرث من Rectangle قد يكسر الكود — لأن تعيين الطول يجب أن يُغيّر العرض أيضاً في المربع.

الكود قبل (❌)

LSP — قبل
public class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
}

public class Square : Rectangle
{
    public override int Width
    {
        set { base.Width = value; base.Height = value; }
    }
    public override int Height
    {
        set { base.Height = value; base.Width = value; }
    }
}

// كود يستخدم Rectangle
void Stretch(Rectangle r)
{
    r.Width = 10;
    r.Height = 5;
    // يتوقع Area = 50، لكن مع Square = 25!
    if (r.Width * r.Height != 50)
        throw new Exception("انتهاك LSP!");
}

الحل (✅)

المشكلة الأساسية في الوراثة الخاطئة. الحل: تجريد مشترك أعلى — كلاهما "شكل" لكن لا يرث أحدهما من الآخر.

LSP — بعد
public abstract class Shape
{
    public abstract int Area();
}

public class Rectangle : Shape
{
    public int Width { get; set; }
    public int Height { get; set; }
    public override int Area() => Width * Height;
}

public class Square : Shape
{
    public int Side { get; set; }
    public override int Area() => Side * Side;
}

علامة انتهاك LSP

إذا وجدت نفسك في الفئة الفرعية تكتب: throw new NotSupportedException() لدالة موجودة في الفئة الأم — فأنت تخالف LSP. أعد التفكير في الوراثة.

فصل الواجهات (ISP)

I
مبدأ فصل الواجهات
Interface Segregation Principle
لا تُجبر العملاء على الاعتماد على واجهات لا يستخدمونها. الأفضل واجهات صغيرة ومتخصصة من واجهة واحدة ضخمة.

مثال: واجهة طابعة ضخمة

لديك واجهة IMultiFunction تدعم الطباعة، المسح، الفاكس. لكن لو عندك طابعة بسيطة تطبع فقط — ستُجبر على تنفيذ دوال لا تحتاجها.

الكود قبل (❌)

ISP — قبل
public interface IMultiFunctionPrinter
{
    void Print();
    void Scan();
    void Fax();
}

public class SimplePrinter : IMultiFunctionPrinter
{
    public void Print() { }
    public void Scan() => throw new NotSupportedException();
    public void Fax() => throw new NotSupportedException();
}

الكود بعد (✅)

ISP — بعد
public interface IPrinter { void Print(); }
public interface IScanner { void Scan(); }
public interface IFax     { void Fax(); }

// الطابعة البسيطة تنفذ فقط ما تحتاجه
public class SimplePrinter : IPrinter
{
    public void Print() => Console.WriteLine("طباعة");
}

// الطابعة متعددة الوظائف تنفذ الكل
public class OfficePrinter : IPrinter, IScanner, IFax
{
    public void Print() { }
    public void Scan() { }
    public void Fax() { }
}

القاعدة

الواجهات الكثيرة الصغيرة أفضل من واجهة واحدة ضخمة. لكن لا تُفرط — واجهات مفرطة في التجزيء قد تكون مربكة.

6

عكس التبعية (DIP)

D
مبدأ عكس التبعية
Dependency Inversion Principle
1) الوحدات عالية المستوى لا يجب أن تعتمد على وحدات منخفضة المستوى — كلاهما يعتمد على التجريد.
2) التجريد لا يجب أن يعتمد على التفاصيل — التفاصيل تعتمد على التجريد.

مثال: خدمة إشعارات

خدمة الطلبات (OrderService) تحتاج إرسال إيميل. لو اعتمدت مباشرة على SmtpClient، فأنت مرتبط بـ SMTP. ماذا لو قررت استخدام SendGrid أو Twilio؟ ستعدّل الكلاس الأساسي.

الكود قبل (❌)

DIP — قبل
public class OrderService
{
    public void PlaceOrder(Order order)
    {
        // ارتبطنا بـ SMTP مباشرة
        var smtp = new SmtpClient("smtp.example.com");
        smtp.Send("noreply@site.com", order.Email,
                  "طلبك", "...");
    }
}

الكود بعد (✅)

DIP — بعد
public interface IEmailSender
{
    Task SendAsync(string to, string body);
}

public class SmtpEmailSender : IEmailSender
{
    public async Task SendAsync(string to, string body) { }
}

public class SendGridEmailSender : IEmailSender
{
    public async Task SendAsync(string to, string body) { }
}

public class OrderService
{
    private readonly IEmailSender _email;
    public OrderService(IEmailSender email) => _email = email;

    public async Task PlaceOrderAsync(Order order)
    {
        await _email.SendAsync(order.Email, "تم طلبك");
    }
}

// في Program.cs
builder.Services.AddScoped<IEmailSender, SmtpEmailSender>();

الآن لتبديل SMTP إلى SendGrid: سطر واحد في DI — وكل الكود الآخر يبقى كما هو.

المكسب

سهولة الاختبار (Mock IEmailSender)، مرونة التبديل (سطر DI)، وقابلية التوسع (إضافة مزود جديد لا يمس المنطق).

7

كشف الأخطاء الشائعة

هذه أعراض شائعة في الكود تُشير إلى انتهاك أحد مبادئ SOLID. جرّب التعرّف عليها بنفسك.

كلاس "Util" ضخم

يحتوي دوال لصيقة بلا صلة — احتمال كبير لمخالفة SRP.

switch يتزايد

كل نوع جديد يتطلب تعديل نفس الدالة — مخالفة OCP.

NotSupportedException

دالة في الفئة الفرعية ترفض تنفيذ واجهة الفئة الأم — مخالفة LSP.

واجهة ضخمة بـ 20 دالة

العملاء ينفذون دوالاً لا يستخدمونها — مخالفة ISP.

new SmtpClient() في المنطق

اعتماد مباشر على البنية التحتية — مخالفة DIP.

اختبار صعب

لا يمكن اختبار الكلاس بدون قاعدة بيانات حقيقية — مخالفة SRP و DIP.

العَرَض المبدأ المخالف الحل المقترح
كلاس يفعل كل شيء SRP قسّمه إلى عدة كلاسات متخصصة
if/switch يتزايد OCP استخدم Strategy / Factory
NotSupportedException LSP أعد تصميم الوراثة أو استخدم الواجهات
واجهة ضخمة ISP قسّم الواجهة إلى واجهات صغيرة
new HttpClient() داخل الكود DIP احقن IHttpClientFactory

قاعدة ذهبية

SOLID ليست قواعد صارمة — بل إرشادات. المبدأ الأساسي هو جعل الكود أسهل للفهم والتغيير. إن لم تحقق هذا الهدف، فمبادئك تحتاج مراجعة.
