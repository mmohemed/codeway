=== lesson
## لماذا يبطئ الاستعلام؟

تخيّل كتاباً من ألف صفحة بلا فهرس، وتبحث عن كلمة "قاعدة". ستقرأ كل الصفحات! هذا ما تفعله قاعدة البيانات عند البحث في عمود بلا فهرس: **تمسح الجدول كاملاً (Full Table Scan)**. مع 10 صفوف لا فرق، لكن مع 10 ملايين صف يصبح الاستعلام بطيئاً جداً.

**الفهرس (Index)** بنية بيانات إضافية مرتبة (غالباً شجرة B-Tree) تشبه فهرس الكتاب: تخبر قاعدة البيانات مباشرة أين توجد الصفوف المطلوبة.

## رؤية الفرق بـ EXPLAIN QUERY PLAN

```sql
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 1;
```

```output
id | parent | notused | detail
2 | 0 | 216 | SCAN orders
```

ركّز على العمود الأخير `detail`، فهو الذي يصف الخطة (الأعمدة الأخرى أرقام داخلية). `SCAN orders` تعني: سأقرأ كل الصفوف. الآن ننشئ فهرساً:

```sql
CREATE INDEX idx_orders_customer ON orders(customer_id);

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 1;
```

```output
id | parent | notused | detail
3 | 0 | 61 | SEARCH orders USING INDEX idx_orders_customer (customer_id=?)
```

أصبحت `SEARCH ... USING INDEX`: قفزة مباشرة إلى الصفوف المطلوبة.

## ماذا نفهرس؟

الأعمدة التي تظهر كثيراً في:

- `WHERE` (البحث والتصفية)
- `JOIN ... ON` (خاصة المفاتيح الأجنبية)
- `ORDER BY` (الترتيب)

> 💡 المفتاح الأساسي مفهرس تلقائياً، وكذلك الأعمدة ذات القيد `UNIQUE`. لكن **المفاتيح الأجنبية لا تُفهرس تلقائياً** في PostgreSQL و SQLite، وفهرستها من أهم تحسينات الأداء.

## الفهرس المركب

فهرس على أكثر من عمود، مفيد عندما تبحث بها معاً:

```sql
CREATE INDEX idx_orders_status_date ON orders(status, order_date);

EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE status = 'مكتمل' AND order_date >= '2025-03-01';
```

```output
id | parent | notused | detail
2 | 0 | 47 | SEARCH orders USING COVERING INDEX idx_orders_status_date (status=? AND order_date>?)
```

> ⚠️ **ترتيب الأعمدة مهم:** فهرس `(status, order_date)` يفيد البحث بـ `status` وحده، أو بـ `status` و `order_date` معاً، لكنه **لا يفيد** البحث بـ `order_date` وحده. مثل دليل الهاتف المرتب بالعائلة ثم الاسم: لا يساعدك في إيجاد كل من اسمه "محمد".

## الفهارس ليست مجانية

| الفائدة | الثمن |
|---|---|
| قراءة وبحث أسرع بكثير | مساحة تخزين إضافية |
| ترتيب أسرع | كل INSERT و UPDATE و DELETE يجب أن يحدّث الفهارس أيضاً |

لذلك لا تفهرس كل عمود. فهرس ما **تبحث به فعلاً**، خاصة في الجداول الكبيرة التي يكثر فيها القراءة.

## الفهرس الفريد

```sql
CREATE UNIQUE INDEX idx_products_name ON products(name);
INSERT INTO products (name, price) VALUES ('لابتوب', 999);
```

```output

ERR: UNIQUE constraint failed: products.name
```

يجمع بين تسريع البحث ومنع التكرار.

## ملخص الدرس

- بدون فهرس تمسح قاعدة البيانات الجدول كاملاً (SCAN).
- `CREATE INDEX اسم ON جدول(أعمدة)` ينشئ فهرساً فيصبح البحث SEARCH.
- فهرس الأعمدة المستخدمة في WHERE و JOIN و ORDER BY، خاصة المفاتيح الأجنبية.
- ترتيب أعمدة الفهرس المركب مهم، والفهارس تبطئ الكتابة قليلاً.

=== lesson
## كل شيء أو لا شيء

تحويل 500 ريال من حساب سعاد إلى حساب مازن يتطلب خطوتين:

1. خصم 500 من سعاد.
2. إضافة 500 لمازن.

ماذا لو انقطعت الكهرباء بعد الخطوة الأولى؟ خُصم المال ولم يصل لأحد! **المعاملة (Transaction)** تجمع عدة عمليات في وحدة واحدة: **إما أن تنجح كلها، أو لا يحدث أي منها**.

## BEGIN و COMMIT

```sql
CREATE TABLE accounts (id INTEGER PRIMARY KEY, owner TEXT, balance INTEGER CHECK (balance >= 0));
INSERT INTO accounts VALUES (1, 'سعاد', 1000), (2, 'مازن', 200);

BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;

SELECT owner, balance FROM accounts;
```

```output
owner | balance
سعاد | 500
مازن | 700
```

- `BEGIN` يبدأ المعاملة.
- `COMMIT` يثبّت كل التغييرات نهائياً.

## ROLLBACK: التراجع

```sql
CREATE TABLE accounts (id INTEGER PRIMARY KEY, owner TEXT, balance INTEGER);
INSERT INTO accounts VALUES (1, 'سعاد', 1000), (2, 'مازن', 200);

BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
DELETE FROM accounts WHERE id = 2;
ROLLBACK;

SELECT owner, balance FROM accounts;
```

```output
owner | balance
سعاد | 1000
مازن | 200
```

`ROLLBACK` ألغى كل ما حدث منذ `BEGIN`، وعادت البيانات كما كانت تماماً. في التطبيقات، يستدعي الكود ROLLBACK تلقائياً عند حدوث أي خطأ أثناء المعاملة.

## خصائص ACID

المعاملات في قواعد البيانات العلائقية تضمن أربع خصائص:

| الخاصية | المعنى |
|---|---|
| **A**tomicity (الذرية) | كل العمليات تنجح، أو لا تنجح أي منها |
| **C**onsistency (الاتساق) | البيانات تنتقل من حالة صحيحة إلى حالة صحيحة، والقيود محترمة دائماً |
| **I**solation (العزل) | المعاملات المتزامنة لا ترى تغييرات بعضها غير المكتملة |
| **D**urability (الديمومة) | بعد COMMIT تبقى البيانات حتى لو تعطل الخادم |

هذه الخصائص هي سبب اعتماد البنوك والمتاجر على قواعد البيانات العلائقية.

## القيود والمعاملات معاً

```sql
CREATE TABLE accounts (id INTEGER PRIMARY KEY, owner TEXT, balance INTEGER CHECK (balance >= 0));
INSERT INTO accounts VALUES (1, 'سعاد', 300), (2, 'مازن', 200);

BEGIN;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
```

```output

ERR: CHECK constraint failed: balance >= 0
```

الخصم الثاني فشل لأنه يخالف `CHECK (balance >= 0)`، وفي هذه الحالة يجب على التطبيق تنفيذ `ROLLBACK` فيُلغى الإيداع الأول أيضاً، فلا يُخلق مال من العدم.

## نقاط الحفظ (SAVEPOINT)

للتراجع عن جزء من المعاملة فقط:

```sql
CREATE TABLE log (msg TEXT);
BEGIN;
INSERT INTO log VALUES ('خطوة 1');
SAVEPOINT before_step2;
INSERT INTO log VALUES ('خطوة 2');
ROLLBACK TO before_step2;
INSERT INTO log VALUES ('خطوة 3');
COMMIT;
SELECT * FROM log;
```

```output
msg
خطوة 1
خطوة 3
```

## ملخص الدرس

- المعاملة تجمع عمليات تنجح كلها أو تُلغى كلها.
- `BEGIN` للبدء، و `COMMIT` للتثبيت، و `ROLLBACK` للتراجع.
- ACID: الذرية والاتساق والعزل والديمومة.
- `SAVEPOINT` و `ROLLBACK TO` للتراجع عن جزء من المعاملة.

## كيف تفكر قاعدة البيانات؟

عندما تكتب استعلاماً، لا تنفّذه قاعدة البيانات مباشرة. بل يقوم **مخطِّط الاستعلامات (Query Planner)** بدراسة طرق التنفيذ الممكنة ويختار الأسرع حسب تقديره. **EXPLAIN** يكشف لك هذه الخطة، وهو الأداة الأولى لأي مطور يبحث عن سبب بطء استعلام.

## EXPLAIN في الأنظمة المختلفة

| النظام | الأمر |
|---|---|
| SQLite | `EXPLAIN QUERY PLAN SELECT ...` |
| PostgreSQL | `EXPLAIN SELECT ...` أو `EXPLAIN ANALYZE SELECT ...` |
| MySQL | `EXPLAIN SELECT ...` |

> 💡 `EXPLAIN ANALYZE` في PostgreSQL **ينفّذ الاستعلام فعلاً** ويعرض الوقت الحقيقي لكل خطوة، وهو الأدق.

## قراءة خطة JOIN

```sql
EXPLAIN QUERY PLAN
SELECT c.name, o.id
FROM customers c
JOIN orders o ON o.customer_id = c.id;
```

```output
id | parent | notused | detail
3 | 0 | 216 | SCAN o
5 | 0 | 45 | SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
```

مسح `orders` كاملاً، ولكل طلب بحث عن العميل بالمفتاح الأساسي `id` (سريع). مع ملايين الطلبات، هذا مقبول لأننا نريدها كلها أصلاً.

## خطة مع شرط على الجدول الأيسر

```sql
EXPLAIN QUERY PLAN
SELECT o.id
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.city = 'جدة';
```

```output
id | parent | notused | detail
3 | 0 | 216 | SCAN o
5 | 0 | 45 | SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
```

بدون فهرس على `orders.customer_id`، لا تستطيع قاعدة البيانات القفز من العميل لطلباته. أضف الفهرس وقارن:

```sql
CREATE INDEX idx_orders_customer ON orders(customer_id);

EXPLAIN QUERY PLAN
SELECT o.id
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.city = 'جدة';
```

```output
id | parent | notused | detail
3 | 0 | 216 | SCAN c
7 | 0 | 53 | SEARCH o USING COVERING INDEX idx_orders_customer (customer_id=?)
```

## أخطاء شائعة تمنع استخدام الفهرس

حتى مع وجود الفهرس، بعض الكتابات تمنع استخدامه:

```sql
CREATE INDEX idx_customers_name ON customers(name);

EXPLAIN QUERY PLAN SELECT city FROM customers WHERE name = 'سارة';
EXPLAIN QUERY PLAN SELECT city FROM customers WHERE trim(name) = 'سارة';
EXPLAIN QUERY PLAN SELECT city FROM customers WHERE name LIKE '%رة';
```

```output
id | parent | notused | detail
3 | 0 | 62 | SEARCH customers USING INDEX idx_customers_name (name=?)

id | parent | notused | detail
2 | 0 | 216 | SCAN customers

id | parent | notused | detail
2 | 0 | 216 | SCAN customers
```

الاستعلام الأول `SEARCH` بالفهرس. أما الآخران فـ `SCAN`: مرّت قاعدة البيانات على كل الصفوف رغم وجود الفهرس.

| الكتابة | لماذا لا يُستخدم الفهرس |
|---|---|
| `WHERE trim(name) = ...` أو `UPPER(email)` | تطبيق دالة على العمود يغيّر القيم المفهرسة |
| `LIKE '%...'` | البداية غير معروفة، والفهرس مرتب من البداية |
| `WHERE price * 1.15 > 100` | عملية حسابية على العمود |

الحل: اكتب الشرط على العمود "نظيفاً"، مثل `price > 100 / 1.15`، أو أنشئ فهرساً على التعبير نفسه.

## قائمة فحص الأداء

1. **اختر الأعمدة المطلوبة** وتجنب `SELECT *`.
2. **فهرس** الأعمدة في WHERE و JOIN و ORDER BY.
3. **راجع الخطة** بـ EXPLAIN قبل وبعد التعديل.
4. **تجنب الدوال على الأعمدة المفهرسة** في الشروط.
5. **استخدم LIMIT** عندما لا تحتاج كل النتائج.
6. **قِس دائماً** ولا تخمّن: التحسين المبني على القياس فقط هو ما يُعتمد عليه.

## ملخص الدرس

- مخطِّط الاستعلامات يختار طريقة التنفيذ، و EXPLAIN يكشفها.
- SCAN مسح كامل، و SEARCH بحث مباشر عبر فهرس أو مفتاح.
- الدوال والعمليات على العمود، و `LIKE '%...'`، تمنع استخدام الفهرس.
- قِس بـ EXPLAIN قبل التحسين وبعده.
