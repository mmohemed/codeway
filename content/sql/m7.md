## بناء الجداول بنفسك

حتى الآن استخدمنا جداول جاهزة. في هذه الوحدة نتعلم **تصميم** قاعدة البيانات وإنشاءها، وهي مهارة تفرّق بين من يكتب استعلامات ومن يبني أنظمة.

## CREATE TABLE

```sql
CREATE TABLE courses (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  level TEXT DEFAULT 'مبتدئ',
  hours INTEGER
);

INSERT INTO courses (title, hours) VALUES ('SQL للمبتدئين', 30);
SELECT * FROM courses;
```

```output
id | title | level | hours
1 | SQL للمبتدئين | مبتدئ | 30
```

لكل عمود: **اسم**، ثم **نوع**، ثم **قيود** اختيارية.

## القيود (Constraints)

القيود قواعد تفرضها قاعدة البيانات نفسها، فلا يمكن لأي تطبيق أو مستخدم كسرها:

| القيد | يضمن |
|---|---|
| `PRIMARY KEY` | قيمة فريدة وغير فارغة تميّز كل صف |
| `NOT NULL` | العمود لا يكون فارغاً |
| `UNIQUE` | لا تتكرر القيمة في العمود |
| `DEFAULT قيمة` | قيمة تلقائية إذا لم تُعطَ قيمة |
| `CHECK (شرط)` | القيمة تحقق شرطاً معيناً |
| `REFERENCES` | القيمة موجودة في جدول آخر (الدرس القادم) |

## CHECK: قواعد العمل في قاعدة البيانات

```sql
CREATE TABLE accounts (
  id INTEGER PRIMARY KEY,
  owner TEXT NOT NULL,
  balance REAL NOT NULL CHECK (balance >= 0),
  type TEXT CHECK (type IN ('جاري', 'توفير'))
);

INSERT INTO accounts (owner, balance, type) VALUES ('سعاد', 500, 'جاري');
INSERT INTO accounts (owner, balance, type) VALUES ('مازن', -100, 'جاري');
```

```output

ERR: CHECK constraint failed: balance >= 0
```

الصف الثاني رُفض لأن الرصيد سالب. لو اعتمدنا على كود التطبيق وحده للتحقق، قد ينسى مطور يوماً ما، أما القيد في قاعدة البيانات فلا ينسى أبداً.

## تعديل بنية الجدول: ALTER TABLE

```sql
CREATE TABLE notes (id INTEGER PRIMARY KEY, body TEXT);
ALTER TABLE notes ADD COLUMN created_at TEXT DEFAULT '2025-01-01';
ALTER TABLE notes RENAME COLUMN body TO content;
INSERT INTO notes (content) VALUES ('أول ملاحظة');
SELECT * FROM notes;
```

```output
id | content | created_at
1 | أول ملاحظة | 2025-01-01
```

| الأمر | الوظيفة |
|---|---|
| `ALTER TABLE t ADD COLUMN ...` | إضافة عمود |
| `ALTER TABLE t RENAME COLUMN a TO b` | إعادة تسمية عمود |
| `ALTER TABLE t RENAME TO new_name` | إعادة تسمية الجدول |
| `ALTER TABLE t DROP COLUMN c` | حذف عمود |
| `DROP TABLE t` | حذف الجدول كاملاً |

## اختيار الأنواع المناسبة

- **المال:** في PostgreSQL و MySQL استخدم `DECIMAL(10, 2)` وليس `FLOAT`، لأن الأرقام العشرية العائمة تسبب أخطاء تقريب مثل `0.1 + 0.2 = 0.30000000000000004`.
- **التواريخ:** استخدم `DATE` أو `TIMESTAMP` وليس نصاً حراً (SQLite تخزنها كنص بصيغة `YYYY-MM-DD`).
- **النصوص القصيرة:** `VARCHAR(100)` يحدد حداً أقصى للطول.

> 💡 SQLite مرنة في الأنواع، لكن PostgreSQL صارمة جداً. صمّم دائماً كأنك تعمل على النظام الصارم.

## ملخص الدرس

- `CREATE TABLE` بأعمدة لكل منها اسم ونوع وقيود.
- القيود (`NOT NULL` و `UNIQUE` و `CHECK` و `DEFAULT`) تحمي البيانات على مستوى قاعدة البيانات.
- `ALTER TABLE` لتعديل البنية، و `DROP TABLE` للحذف.
- اختر النوع المناسب، خاصة للمال والتواريخ.

## ربط الجداول بأمان

في متجرنا، `orders.customer_id` يشير إلى `customers.id`. لكن ماذا يمنع إدخال طلب لعميل رقمه 999 غير موجود؟ أو حذف عميل له طلبات فتبقى طلباته "يتيمة"؟ الجواب: **المفتاح الأجنبي (Foreign Key)**.

## المفتاح الأساسي والأجنبي

| | المفتاح الأساسي (PK) | المفتاح الأجنبي (FK) |
|---|---|---|
| الوظيفة | يميّز كل صف في جدوله | يشير إلى مفتاح أساسي في جدول آخر |
| التكرار | لا يتكرر | يمكن أن يتكرر (عميل له طلبات كثيرة) |
| مثال | `customers.id` | `orders.customer_id` |

## تعريف المفتاح الأجنبي

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE authors (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL
);

CREATE TABLE books (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  author_id INTEGER NOT NULL REFERENCES authors(id)
);

INSERT INTO authors (id, name) VALUES (1, 'نجيب محفوظ');
INSERT INTO books (title, author_id) VALUES ('الثلاثية', 1);
INSERT INTO books (title, author_id) VALUES ('كتاب مجهول', 99);
```

```output

ERR: FOREIGN KEY constraint failed
```

رُفض الكتاب الثاني لأن المؤلف رقم 99 غير موجود. هذا يسمى **سلامة المرجعية (Referential Integrity)**.

> ⚠️ في SQLite يجب تفعيل المفاتيح الأجنبية بـ `PRAGMA foreign_keys = ON;` في كل اتصال، أما PostgreSQL و MySQL فتفرضها دائماً.

## ماذا يحدث عند حذف الأب؟

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE authors (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE books (id INTEGER PRIMARY KEY, title TEXT,
                    author_id INTEGER REFERENCES authors(id));
INSERT INTO authors VALUES (1, 'طه حسين');
INSERT INTO books (title, author_id) VALUES ('الأيام', 1);

DELETE FROM authors WHERE id = 1;
```

```output

ERR: FOREIGN KEY constraint failed
```

لا يمكن حذف مؤلف له كتب. يمكنك تغيير هذا السلوك بخيار `ON DELETE`:

| الخيار | عند حذف الأب |
|---|---|
| (الافتراضي) `RESTRICT` أو `NO ACTION` | يُرفض الحذف |
| `CASCADE` | تُحذف الصفوف التابعة تلقائياً |
| `SET NULL` | تصبح قيمة المفتاح الأجنبي NULL |

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE posts (id INTEGER PRIMARY KEY, title TEXT);
CREATE TABLE comments (
  id INTEGER PRIMARY KEY,
  body TEXT,
  post_id INTEGER REFERENCES posts(id) ON DELETE CASCADE
);
INSERT INTO posts VALUES (1, 'منشور');
INSERT INTO comments (body, post_id) VALUES ('رائع', 1), ('شكراً', 1);

DELETE FROM posts WHERE id = 1;
SELECT COUNT(*) AS comments_left FROM comments;
```

```output
comments_left
0
```

حذف المنشور حذف تعليقاته تلقائياً. مناسب للتعليقات، لكن **خطير** للطلبات والفواتير، فلا تستخدم CASCADE إلا حيث يكون منطقياً فعلاً.

## المفتاح الأساسي المركب

جدول `order_items` لا يحتاج `id`، فكل سطر يتميز بتركيبة (الطلب، المنتج):

```sql-error
CREATE TABLE order_items (
  order_id INTEGER REFERENCES orders(id),
  product_id INTEGER REFERENCES products(id),
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (order_id, product_id)
);
```

## ملخص الدرس

- المفتاح الأجنبي `REFERENCES جدول(عمود)` يضمن أن القيمة موجودة في الجدول الآخر.
- يمنع إدخال مراجع غير موجودة، ويمنع حذف صف له صفوف تابعة.
- `ON DELETE CASCADE` أو `SET NULL` لتغيير سلوك الحذف.
- في SQLite فعّل المفاتيح الأجنبية بـ `PRAGMA foreign_keys = ON`.

## التكرار عدو البيانات

انظر إلى هذا الجدول "السهل":

| order_id | customer | customer_phone | products |
|---|---|---|---|
| 1 | أحمد | 0501111111 | لابتوب، سماعة |
| 2 | أحمد | 0501111111 | رواية |
| 3 | سارة | 0502222222 | قميص |

يبدو مريحاً، لكنه مليء بالمشاكل:

- **مشكلة التعديل:** إذا غيّر أحمد رقمه، يجب تعديل كل طلباته، وإن نسيت واحداً أصبحت البيانات متناقضة.
- **مشكلة الإدخال:** لا يمكن تسجيل عميل جديد قبل أن يطلب شيئاً.
- **مشكلة الحذف:** حذف طلب سارة الوحيد يمحو معلوماتها كعميلة.
- **مشكلة البحث:** كيف تجد كل من اشترى "سماعة" وهي مدفونة داخل نص؟

**التطبيع (Normalization)** عملية تنظيم الجداول لإزالة هذا التكرار، عبر قواعد تسمى **الصيغ الطبيعية**.

## الصيغة الأولى (1NF): قيمة واحدة في كل خلية

العمود `products` فيه عدة قيم مفصولة بفواصل. هذا يخالف 1NF. الحل: كل منتج في صف مستقل:

| order_id | product |
|---|---|
| 1 | لابتوب |
| 1 | سماعة |
| 2 | رواية |

## الصيغة الثانية (2NF): كل عمود يعتمد على المفتاح كاملاً

في جدول مفتاحه مركب `(order_id, product_id)`، العمود `product_name` يعتمد على `product_id` فقط وليس على المفتاح كاملاً. الحل: نقله لجدول المنتجات.

## الصيغة الثالثة (3NF): لا شيء يعتمد على غير المفتاح

في جدول الطلبات، `customer_phone` يعتمد على `customer` وليس على `order_id`. الحل: جدول مستقل للعملاء، والطلب يحفظ رقم العميل فقط.

> 💡 الملخص الشهير: كل عمود يجب أن يعتمد على **المفتاح، والمفتاح كاملاً، ولا شيء غير المفتاح**.

## النتيجة: تصميم متجرنا

هكذا وصلنا للتصميم الذي نستخدمه طوال الدورة: `customers` و `products` و `orders` و `order_items`. كل معلومة محفوظة في **مكان واحد فقط**، والجداول مرتبطة بالمفاتيح. ولإعادة تجميع البيانات نستخدم JOIN:

```sql
SELECT o.id AS order_id, c.name AS customer, p.name AS product
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.id IN (101, 102)
ORDER BY o.id, p.id;
```

```output
order_id | customer | product
101 | أحمد | لابتوب
101 | أحمد | سماعة
102 | سارة | قميص
102 | سارة | رواية
```

## متى نكسر التطبيع؟

أحياناً نكرر بيانات **عمداً** (Denormalization) لسببين مقبولين:

- **الأداء:** في التقارير الضخمة، تجنب JOINs كثيرة قد يستحق التكرار.
- **التاريخ:** لاحظ أن `order_items` فيه `unit_price` رغم وجود السعر في `products`. لماذا؟ لأن سعر المنتج قد يتغير غداً، لكن الفاتورة يجب أن تحفظ السعر **وقت الشراء**. هذا ليس تكراراً خاطئاً بل معلومة مختلفة.

## ملخص الدرس

- التكرار يسبب تناقض البيانات ومشاكل في الإدخال والتعديل والحذف.
- 1NF: قيمة واحدة في كل خلية. 2NF: الاعتماد على المفتاح كاملاً. 3NF: لا اعتماد على غير المفتاح.
- كل معلومة في مكان واحد، و JOIN يعيد تجميعها.
- كسر التطبيع مقبول أحياناً للأداء أو لحفظ قيم تاريخية.

## الرسم قبل البناء

قبل كتابة `CREATE TABLE`، يرسم المصممون **مخطط الكيانات والعلاقات (ER Diagram)**: صورة توضح الجداول وأعمدتها وكيف ترتبط. هو لغة مشتركة بين المطورين ومديري المنتجات، ويكشف أخطاء التصميم قبل أن تصبح مكلفة.

## المكونات الثلاثة

| المكوّن | المعنى | في متجرنا |
|---|---|---|
| **الكيان (Entity)** | شيء نحفظ عنه بيانات، ويصبح جدولاً | عميل، منتج، طلب |
| **الخاصية (Attribute)** | معلومة عن الكيان، وتصبح عموداً | الاسم، السعر |
| **العلاقة (Relationship)** | كيف يرتبط كيانان | العميل **يقدّم** طلبات |

## أنواع العلاقات

### واحد لواحد (1:1)

مستخدم له ملف شخصي واحد. نضع المفتاح الأجنبي في أحد الجدولين مع قيد `UNIQUE`.

### واحد لمتعدد (1:N)

الأكثر شيوعاً: عميل واحد له **طلبات كثيرة**، وكل طلب لعميل واحد. القاعدة: **المفتاح الأجنبي يوضع في جهة "المتعدد"**، أي `orders.customer_id`.

### متعدد لمتعدد (N:M)

طلب فيه **منتجات كثيرة**، ومنتج يظهر في **طلبات كثيرة**. لا يمكن تمثيلها بمفتاح أجنبي واحد، فنحتاج **جدولاً وسيطاً (Junction Table)** فيه مفتاحان أجنبيان. وهذا بالضبط دور `order_items`.

## مخطط متجرنا

```text
customers 1 ──────< N orders 1 ──────< N order_items N >────── 1 products
   id 🔑               id 🔑                order_id  →               id 🔑
   name                customer_id →        product_id →              name
   city                order_date           quantity                  price
   email               status               unit_price                stock

employees ─┐
   id 🔑    │ manager_id → employees.id  (علاقة 1:N مع نفس الجدول)
   manager_id ←┘
```

- العلامة `<` تشير لجهة "المتعدد"، و `1` لجهة "الواحد".
- السهم `→` يعني مفتاحاً أجنبياً.

## من المتطلبات إلى المخطط

عندما يقول لك العميل: "أريد نظاماً لمدرسة: كل **طالب** يسجّل في **مقررات** كثيرة، وكل مقرر يدرّسه **معلم** واحد، والمعلم يدرّس مقررات عدة"، اتبع هذه الخطوات:

1. **الأسماء** في الوصف كيانات: طالب، مقرر، معلم.
2. **الأفعال** علاقات: يسجّل، يدرّس.
3. **حدد نوع كل علاقة:** طالب ↔ مقرر (N:M، تحتاج جدولاً وسيطاً `enrollments`)، معلم ↔ مقرر (1:N، المفتاح في `courses.teacher_id`).
4. **أضف الخصائص**، وما يخص العلاقة نفسها (مثل الدرجة) يوضع في الجدول الوسيط.

## أدوات الرسم

- **dbdiagram.io:** تكتب الجداول نصاً فيرسمها تلقائياً.
- **draw.io:** رسم حر مجاني.
- **pgAdmin و MySQL Workbench:** يولّدان المخطط من قاعدة بيانات موجودة.

## ملخص الدرس

- مخطط ER يرسم الكيانات (جداول) والخصائص (أعمدة) والعلاقات.
- 1:N: المفتاح الأجنبي في جهة المتعدد.
- N:M: جدول وسيط بمفتاحين أجنبيين، وخصائص العلاقة توضع فيه.
- ابدأ من المتطلبات: الأسماء كيانات، والأفعال علاقات.

--- exercise
حوّل تصميم المدرسة من الدرس إلى جداول:

1. `teachers` (`id`، `name`).
2. `courses` (`id`، `title`، `teacher_id` يشير إلى `teachers`).
3. `students` (`id`، `name`).
4. الجدول الوسيط `enrollments` (`student_id` و `course_id` كمفتاح أساسي مركب، و `grade`).

البيانات: المعلم 1 `أ. نوال`، المقرران 1 `رياضيات` و 2 `فيزياء` يدرّسهما المعلم 1، الطالبان 1 `رغد` و 2 `حمزة`. رغد سجلت في المقررين بدرجتي 90 و 85، وحمزة في الرياضيات بدرجة 70.

أخيراً اعرض اسم الطالب `student` وعنوان المقرر `course` والدرجة `grade` مرتبة حسب اسم الطالب ثم المقرر.

~~~starter
-- الجداول

-- البيانات

-- الاستعلام النهائي

~~~
~~~expected
student | course | grade
حمزة | رياضيات | 70
رغد | رياضيات | 90
رغد | فيزياء | 85
~~~
~~~solution
CREATE TABLE teachers (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE courses (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  teacher_id INTEGER REFERENCES teachers(id)
);
CREATE TABLE students (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE enrollments (
  student_id INTEGER REFERENCES students(id),
  course_id INTEGER REFERENCES courses(id),
  grade INTEGER,
  PRIMARY KEY (student_id, course_id)
);

INSERT INTO teachers VALUES (1, 'أ. نوال');
INSERT INTO courses VALUES (1, 'رياضيات', 1), (2, 'فيزياء', 1);
INSERT INTO students VALUES (1, 'رغد'), (2, 'حمزة');
INSERT INTO enrollments VALUES (1, 1, 90), (1, 2, 85), (2, 1, 70);

SELECT s.name AS student, c.title AS course, e.grade
FROM enrollments e
JOIN students s ON s.id = e.student_id
JOIN courses c ON c.id = e.course_id
ORDER BY s.name, c.title;
~~~
