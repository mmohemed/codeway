=== lesson
## لماذا نحتاج «سير عمل» متفق عليه؟

عندما يعمل خمسة مطورين على نفس المستودع، يجب أن يتفقوا على أسئلة مثل: من أين أُنشئ فرعي؟ متى ندمج؟ كيف نصدر نسخة جديدة؟ كيف نصلح خطأ عاجلاً في الإنتاج دون إدخال ميزات ناقصة؟ الإجابة على هذه الأسئلة تسمى **سير العمل (Workflow)**.

## Git Flow

**Git Flow** نموذج مشهور يعتمد على فرعين دائمين وثلاثة أنواع من الفروع المؤقتة:

| الفرع | الغرض | يتفرع من | يُدمج في |
|---|---|---|---|
| `main` | النسخة المنشورة للمستخدمين فقط | - | - |
| `develop` | تجميع الميزات الجاهزة للإصدار القادم | `main` | - |
| `feature/*` | ميزة واحدة قيد التطوير | `develop` | `develop` |
| `release/*` | تجهيز إصدار: اختبار وإصلاحات صغيرة | `develop` | `main` و `develop` |
| `hotfix/*` | إصلاح عاجل في الإنتاج | `main` | `main` و `develop` |

## دورة ميزة في Git Flow

```terminal-new
$ git init
Initialized empty Git repository in /project/.git/
$ echo "v1" > app.txt
$ git add .
$ git commit -m "الإصدار الأول"
[main (root-commit) 6100b54] الإصدار الأول
 1 file changed, 1 insertion(+)
 create mode 100644 app.txt
$ git tag v1.0.0
$ git switch -c develop
Switched to a new branch 'develop'
$ git switch -c feature/wishlist
Switched to a new branch 'feature/wishlist'
$ echo "قائمة الأمنيات" > wishlist.txt
$ git add .
$ git commit -m "feat: قائمة الأمنيات"
[feature/wishlist 208ee81] feat: قائمة الأمنيات
 1 file changed, 1 insertion(+)
 create mode 100644 wishlist.txt
$ git switch develop
Switched to branch 'develop'
$ git merge --no-ff feature/wishlist
Merge made by the 'ort' strategy.
 wishlist.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 wishlist.txt
$ git branch -d feature/wishlist
Deleted branch feature/wishlist (was 208ee81).
```

الميزة الآن في `develop`، وليست عند المستخدمين بعد. الخيار `--no-ff` يجبر Git على إنشاء commit دمج حتى لو أمكن التقديم السريع، فيبقى في التاريخ أثر واضح لكل ميزة متى دخلت، وهو المعتاد في Git Flow.

## الإصدار: release

عندما تجتمع ميزات كافية، نفتح فرع إصدار، ثم ندمجه في `main` ونضع عليه **وسماً (tag)** برقم الإصدار:

```terminal
$ git switch -c release/1.1.0
Switched to a new branch 'release/1.1.0'
$ echo "1.1.0" > version.txt
$ git add .
$ git commit -m "chore: رفع رقم الإصدار إلى 1.1.0"
[release/1.1.0 e198c81] chore: رفع رقم الإصدار إلى 1.1.0
 1 file changed, 1 insertion(+)
 create mode 100644 version.txt
$ git switch main
Switched to branch 'main'
$ git merge --no-ff release/1.1.0
Merge made by the 'ort' strategy.
 version.txt  | 1 +
 wishlist.txt | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 version.txt
 create mode 100644 wishlist.txt
$ git tag -a v1.1.0 -m "الإصدار 1.1.0"
$ git switch develop
Switched to branch 'develop'
$ git merge --no-ff release/1.1.0
Merge made by the 'ort' strategy.
 version.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 version.txt
$ git branch -d release/1.1.0
Deleted branch release/1.1.0 (was e198c81).
$ git tag
v1.0.0
v1.1.0
```

**الوسم (tag)** اسم ثابت يشير لـ commit معيّن، يُستخدم لترقيم الإصدارات. على عكس الفرع، الوسم لا يتحرك. والخيار `-a` ينشئ وسماً مشروحاً برسالة، وهو المستحسن للإصدارات. ولرفع الوسوم: `git push --tags`.

## الإصلاح العاجل: hotfix

اكتُشف خطأ خطير في الإنتاج، و `develop` فيه ميزات غير جاهزة. نتفرع من `main` مباشرة:

```terminal
$ git switch main
Switched to branch 'main'
$ git switch -c hotfix/1.1.1
Switched to a new branch 'hotfix/1.1.1'
$ echo "v1-fixed" > app.txt
$ git commit -am "fix: إصلاح انهيار صفحة الدفع"
[hotfix/1.1.1 cb3e64b] fix: إصلاح انهيار صفحة الدفع
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git switch main
Switched to branch 'main'
$ git merge --no-ff hotfix/1.1.1
Merge made by the 'ort' strategy.
 app.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git tag -a v1.1.1 -m "إصلاح عاجل"
$ git switch develop
Switched to branch 'develop'
$ git merge --no-ff hotfix/1.1.1
Merge made by the 'ort' strategy.
 app.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log --oneline -1 main
6656988 (tag: v1.1.1, main) Merge branch 'hotfix/1.1.1'
```

> ⚠️ لا تنسَ دمج الـ hotfix في `develop` أيضاً، وإلا سيعود الخطأ في الإصدار القادم!

## البديل الأبسط: GitHub Flow

Git Flow مناسب للمنتجات ذات الإصدارات المرقّمة (تطبيقات الجوال والمكتبات). أما المواقع والتطبيقات التي تُنشر عدة مرات يومياً، فتفضّل **GitHub Flow** الأبسط:

1. `main` دائماً جاهز للنشر.
2. لكل مهمة فرع من `main`.
3. Pull Request ومراجعة واختبارات آلية.
4. دمج في `main` ونشر تلقائي.

## ترقيم الإصدارات الدلالي (SemVer)

الأرقام في `v1.1.0` لها معنى: **MAJOR.MINOR.PATCH**:

| الجزء | يزيد عند | مثال |
|---|---|---|
| MAJOR | تغيير يكسر التوافق | `1.4.2` ← `2.0.0` |
| MINOR | ميزة جديدة متوافقة | `1.4.2` ← `1.5.0` |
| PATCH | إصلاح خطأ | `1.4.2` ← `1.4.3` |

## ملخص الدرس

- Git Flow: `main` للإنتاج، و `develop` للتجميع، وفروع `feature` و `release` و `hotfix`.
- hotfix يتفرع من `main` ويُدمج في `main` و `develop` معاً.
- `git tag -a v1.2.0 -m "..."` يضع وسماً ثابتاً على الإصدار.
- GitHub Flow أبسط: `main` وفروع قصيرة و Pull Requests.
- SemVer: MAJOR لكسر التوافق، و MINOR للميزات، و PATCH للإصلاحات.

=== lesson
## رسالة commit هي توثيق المشروع

بعد سنة، ستقرأ أنت أو زميلك تاريخ المشروع لتفهم **لماذا** تغيّر شيء ما. قارن بين تاريخين:

```text
تاريخ سيء:                     تاريخ احترافي:
fix                             fix(cart): منع الكمية السالبة في السلة
update                          feat(auth): تسجيل الدخول بحساب Google
asdf                            docs: شرح طريقة التثبيت في README
final changes                   refactor(api): توحيد معالجة الأخطاء
```

## قواعد الرسالة الجيدة

1. **سطر عنوان قصير**: 50 حرفاً تقريباً، يلخص التغيير.
2. **صيغة الأمر أو الوصف المباشر**: «إضافة البحث» أو `Add search`، وليس «أضفت البحث أمس».
3. **commit واحد لتغيير منطقي واحد**: لا تخلط إصلاح خطأ مع ميزة جديدة.
4. **اشرح «لماذا» في جسم الرسالة** إذا لم يكن واضحاً من الكود.

## Conventional Commits

معيار تتبعه آلاف المشاريع، يبدأ كل عنوان بنوع التغيير:

```text
<type>(<scope>): <description>
```

| النوع | متى |
|---|---|
| `feat` | ميزة جديدة للمستخدم |
| `fix` | إصلاح خطأ |
| `docs` | توثيق فقط |
| `style` | تنسيق لا يغير السلوك (مسافات، فواصل) |
| `refactor` | إعادة هيكلة بلا تغيير سلوك |
| `test` | إضافة أو تعديل اختبارات |
| `chore` | مهام صيانة: إعدادات، تحديث حزم |
| `perf` | تحسين أداء |

`scope` اختياري ويحدد الجزء المتأثر: `fix(cart)` و `feat(auth)`. وعلامة `!` بعد النوع تعني تغييراً يكسر التوافق: `feat!: حذف واجهة v1`.

> 💡 الفائدة ليست جمالية فقط: أدوات مثل semantic-release تقرأ هذه الأنواع وتحسب رقم الإصدار التالي وتولّد سجل التغييرات (CHANGELOG) تلقائياً: `fix` يرفع PATCH، و `feat` يرفع MINOR.

## مثال عملي

```terminal-new
$ git init
Initialized empty Git repository in /project/.git/
$ echo "# CodeWay" > README.md
$ git add .
$ git commit -m "chore: إعداد المشروع"
[main (root-commit) 507e003] chore: إعداد المشروع
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ echo "function login() {}" > auth.js
$ git add .
$ git commit -m "feat(auth): إضافة تسجيل الدخول"
[main 5b7a53a] feat(auth): إضافة تسجيل الدخول
 1 file changed, 1 insertion(+)
 create mode 100644 auth.js
$ echo "## التثبيت" >> README.md
$ git commit -am "docs: شرح خطوات التثبيت"
[main fc83f95] docs: شرح خطوات التثبيت
 1 file changed, 1 insertion(+)
$ git log --oneline
fc83f95 (HEAD -> main) docs: شرح خطوات التثبيت
5b7a53a feat(auth): إضافة تسجيل الدخول
507e003 chore: إعداد المشروع
```

## أخطأت في الرسالة؟ amend

إذا كتبت رسالة خاطئة في **آخر** commit ولم ترفعه بعد، صحّحها بـ `--amend`:

```terminal
$ echo "function logout() {}" >> auth.js
$ git commit -am "update"
[main 48e34f4] update
 1 file changed, 1 insertion(+)
$ git commit --amend -m "feat(auth): إضافة تسجيل الخروج"
[main 9ccbc37] feat(auth): إضافة تسجيل الخروج
 Date: Mon Jan 6 10:04:00 2025 +0300
 1 file changed, 1 insertion(+)
$ git log --oneline -2
9ccbc37 (HEAD -> main) feat(auth): إضافة تسجيل الخروج
fc83f95 docs: شرح خطوات التثبيت
```

`--amend` يستبدل آخر commit بآخر جديد. ويمكنه أيضاً إضافة ملف نسيته: `git add file` ثم `git commit --amend`.

> ⚠️ مثل rebase، لا تستخدم `--amend` على commit رفعته وشاركه غيرك، لأنه يغيّر معرّفه.

## ملخص الدرس

- الرسالة الجيدة قصيرة وواضحة وتشرح التغيير، و commit واحد لكل تغيير منطقي.
- Conventional Commits: `type(scope): description` مثل `fix(cart): ...`.
- الأنواع الأساسية: feat و fix و docs و refactor و test و chore.
- `git commit --amend -m "..."` يصحح آخر commit لم يُرفع.

=== lesson
## ملفات لا مكان لها في المستودع

ليس كل ملف في مجلد المشروع يجب أن يُحفظ في Git:

| النوع | أمثلة | لماذا نتجاهله |
|---|---|---|
| الحزم المثبتة | `node_modules/` | ضخمة جداً، وتُنزَّل بـ `npm install` |
| مخرجات البناء | `dist/` و `build/` | تُولَّد من الكود بأمر البناء |
| الأسرار | `.env` | كلمات مرور ومفاتيح API! |
| السجلات | `*.log` | تتغير باستمرار وبلا قيمة |
| ملفات النظام والمحرر | `.DS_Store` و `.vscode/` | تخص جهازك فقط |

> ⚠️ رفع ملف `.env` فيه مفاتيح إلى مستودع عام من أخطر الأخطاء الأمنية: برامج آلية تمسح GitHub باستمرار بحثاً عن المفاتيح المسرّبة، وقد تُستغل خلال دقائق.

## ملف .gitignore

ملف نصي في جذر المشروع، كل سطر فيه نمط لملفات يتجاهلها Git:

```terminal-new
$ git init
Initialized empty Git repository in /project/.git/
$ echo "console.log('app')" > src/app.js
$ echo "module" > node_modules/react/index.js
$ echo "API_KEY=abc123" > .env
$ echo "error at line 5" > debug.log
$ echo "bundle" > dist/main.js
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.env
	debug.log
	dist/
	node_modules/
	src/

nothing added to commit but untracked files present (use "git add" to track)
```

كل شيء ظاهر، حتى الأسرار! لننشئ `.gitignore`:

```terminal
$ cat > .gitignore <<EOF
> node_modules/
> dist/
> .env
> *.log
> EOF
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	src/

nothing added to commit but untracked files present (use "git add" to track)
```

الآن لا يظهر إلا `.gitignore` و `src/`، وهذا ما نريد حفظه:

```terminal
$ git add .
$ git commit -m "chore: إعداد المشروع"
[main (root-commit) 8afdf69] chore: إعداد المشروع
 2 files changed, 5 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 src/app.js
$ git ls-files
.gitignore
src/app.js
```

## صيغة الأنماط

| النمط | يطابق |
|---|---|
| `secret.txt` | أي ملف بهذا الاسم في أي مجلد |
| `*.log` | كل الملفات المنتهية بـ `.log` |
| `build/` | مجلد `build` وكل ما فيه |
| `/config.js` | `config.js` في الجذر فقط |
| `docs/**/*.pdf` | كل ملفات pdf داخل `docs` بأي عمق |
| `!keep.log` | استثناء: لا تتجاهل هذا الملف |
| `# تعليق` | سطر تعليق |

## لماذا يُتجاهل هذا الملف؟

`git check-ignore -v` يخبرك أي سطر في `.gitignore` سبب التجاهل:

```terminal
$ git check-ignore -v debug.log .env
.gitignore:4:*.log	debug.log
.gitignore:3:.env	.env
```

## أضفت الملف قبل .gitignore؟

`.gitignore` يعمل على الملفات **غير المتتبَّعة فقط**. إذا كان الملف محفوظاً في Git من قبل، فإضافته لـ `.gitignore` لا تكفي:

```terminal-new
$ git init
Initialized empty Git repository in /project/.git/
$ echo "DB_PASSWORD=123" > .env
$ echo "app" > app.js
$ git add .
$ git commit -m "البداية"
[main (root-commit) 1e60919] البداية
 2 files changed, 2 insertions(+)
 create mode 100644 .env
 create mode 100644 app.js
$ echo ".env" > .gitignore
$ echo "DB_PASSWORD=456" > .env
$ git status --short
 M .env
?? .gitignore
```

ما زال Git يتتبع `.env`! الحل: أزله من التتبع مع إبقائه على جهازك بـ `git rm --cached`:

```terminal
$ git rm --cached .env
rm '.env'
$ git add .gitignore
$ git commit -m "chore: إيقاف تتبع ملف الأسرار"
[main 58ca881] chore: إيقاف تتبع ملف الأسرار
 2 files changed, 1 insertion(+), 1 deletion(-)
 delete mode 100644 .env
 create mode 100644 .gitignore
$ git status --short
$ ls -a
.env  .git  .gitignore  app.js
```

> ⚠️ إذا رُفعت الأسرار إلى GitHub فهي في التاريخ حتى بعد حذفها. الحل الصحيح: **غيّر كلمات المرور والمفاتيح فوراً**، ثم نظّف التاريخ إن لزم.

## قوالب جاهزة

لا تكتب `.gitignore` من الصفر: GitHub يقترح قالباً عند إنشاء المستودع (Node و Python و Android...)، والمستودع `github/gitignore` يحتوي قوالب لكل اللغات تقريباً. وأدوات مثل Vite و Next.js تنشئ الملف تلقائياً مع المشروع.

## ملخص الدرس

- `.gitignore` يمنع Git من تتبع ملفات مثل `node_modules/` و `.env` و `dist/` و `*.log`.
- الأنماط تدعم `*` و `/` في النهاية للمجلدات و `!` للاستثناء.
- `git check-ignore -v` يشرح سبب تجاهل ملف.
- لملف متتبَّع مسبقاً: `git rm --cached file` ثم commit.
- الأسرار المرفوعة تُعتبر مسرّبة: غيّرها فوراً.
