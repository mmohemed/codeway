=== lesson
## لماذا الفروع؟

تخيّل أن موقعك يعمل الآن عند العملاء، وتريد إضافة ميزة جديدة تستغرق أسبوعاً. لو عدّلت مباشرة على النسخة الرئيسية، سيصبح الموقع نصف جاهز طوال الأسبوع. وإذا ظهر خطأ عاجل في المنتصف، لا تستطيع إصلاحه دون نشر الميزة الناقصة معه.

**الفرع (branch)** خط تطوير مستقل: تعمل عليه بحرية، والفرع الرئيسي `main` يبقى سليماً حتى تدمج عملك عندما يجهز.

> 💡 الفرع في Git خفيف جداً: مجرد مؤشر يشير إلى commit. لذلك إنشاء الفروع فوري، والمحترفون ينشئون فرعاً لكل مهمة مهما كانت صغيرة.

## عرض الفروع وإنشاؤها

```terminal-new
$ git init
Initialized empty Git repository in /project/.git/
$ echo "<h1>متجري</h1>" > index.html
$ git add .
$ git commit -m "الصفحة الرئيسية"
[main (root-commit) 1f3d1f4] الصفحة الرئيسية
 1 file changed, 1 insertion(+)
 create mode 100644 index.html
$ git branch
* main
$ git branch feature-cart
$ git branch
  feature-cart
* main
```

`git branch` يعرض الفروع، والنجمة `*` على الفرع الحالي. لاحظ أن `git branch feature-cart` أنشأ الفرع لكنه **لم ينقلك إليه**.

## الانتقال بين الفروع: git switch

```terminal
$ git switch feature-cart
Switched to branch 'feature-cart'
$ echo "<div>سلة المشتريات</div>" > cart.html
$ git add cart.html
$ git commit -m "إضافة صفحة السلة"
[feature-cart 3193002] إضافة صفحة السلة
 1 file changed, 1 insertion(+)
 create mode 100644 cart.html
$ ls
cart.html  index.html
$ git switch main
Switched to branch 'main'
$ ls
index.html
```

لاحظ ما حدث: عندما عدت إلى `main` **اختفى** `cart.html` من المجلد! الملف لم يُحذف، بل هو محفوظ في الفرع `feature-cart`، و Git يعرض لك دائماً ملفات الفرع الذي تقف عليه.

## إنشاء فرع والانتقال إليه معاً

الأكثر استخداماً: `git switch -c` ينشئ الفرع وينقلك إليه في خطوة واحدة:

```terminal
$ git switch -c fix-title
Switched to a new branch 'fix-title'
$ git branch
  feature-cart
* fix-title
  main
```

> 💡 ستجد في الشروحات القديمة `git checkout -b name`، وهو يعمل نفس الشيء. `git switch` أحدث وأوضح، و `checkout` ما زال مدعوماً.

## رؤية الفروع في السجل

`--all` يعرض commits كل الفروع، والأقواس توضح أين يقف كل فرع:

```terminal
$ git log --oneline --all
3193002 (feature-cart) إضافة صفحة السلة
1f3d1f4 (HEAD -> fix-title, main) الصفحة الرئيسية
```

## حذف فرع

بعد دمج الفرع لا حاجة له. `-d` يحذفه بأمان، ويرفض إن كان فيه عمل غير مدموج:

```terminal
$ git switch main
Switched to branch 'main'
$ git branch -d fix-title
Deleted branch fix-title (was 1f3d1f4).
$ git branch -d feature-cart
ERR: error: the branch 'feature-cart' is not fully merged.
ERR: hint: If you are sure you want to delete it, run 'git branch -D feature-cart'
```

`fix-title` حُذف لأنه لا يحتوي شيئاً جديداً، أما `feature-cart` فرفض Git حذفه لأن فيه commit لم يُدمج بعد. لو كنت متأكداً أنك تريد التخلص منه استخدم `-D`.

## تسمية الفروع

| النوع | مثال |
|---|---|
| ميزة جديدة | `feature/login` |
| إصلاح خطأ | `fix/cart-total` |
| إصلاح عاجل في الإنتاج | `hotfix/payment-crash` |
| تحسين بلا تغيير سلوك | `refactor/api-client` |

## ملخص الدرس

- الفرع خط تطوير مستقل يحمي `main` من العمل غير المكتمل.
- `git branch` يعرض الفروع، و `git branch name` ينشئ فرعاً.
- `git switch name` ينتقل، و `git switch -c name` ينشئ وينتقل.
- `git branch -d` يحذف فرعاً مدموجاً، و `-D` يحذفه إجبارياً.

## الدمج: git merge

انتهيت من العمل على فرع، والآن تريد إدخال تغييراته في `main`. الطريقة: **قف على الفرع الذي سيستقبل التغييرات**، ثم ادمج الفرع الآخر فيه.

## دمج التقديم السريع (Fast-forward)

إذا لم يتغير `main` منذ أنشأت فرعك، فالدمج بسيط جداً: Git يحرّك مؤشر `main` للأمام فقط:

```terminal-new
$ git init
Initialized empty Git repository in /project/.git/
$ echo "قائمة الطعام" > menu.txt
$ git add .
$ git commit -m "بداية القائمة"
[main (root-commit) 1542df4] بداية القائمة
 1 file changed, 1 insertion(+)
 create mode 100644 menu.txt
$ git switch -c add-drinks
Switched to a new branch 'add-drinks'
$ echo "- قهوة" >> menu.txt
$ git commit -am "إضافة القهوة"
[add-drinks 00fb36f] إضافة القهوة
 1 file changed, 1 insertion(+)
$ echo "- شاي" >> menu.txt
$ git commit -am "إضافة الشاي"
[add-drinks e46c381] إضافة الشاي
 1 file changed, 1 insertion(+)
$ git switch main
Switched to branch 'main'
$ git merge add-drinks
Updating 1542df4..e46c381
Fast-forward
 menu.txt | 2 ++
 1 file changed, 2 insertions(+)
$ git log --oneline
e46c381 (HEAD -> main, add-drinks) إضافة الشاي
00fb36f إضافة القهوة
1542df4 بداية القائمة
```

كلمة `Fast-forward` تعني أنه لم يُنشأ commit جديد، بل أصبح `main` يشير لآخر commit في `add-drinks`.

```text
قبل:   A ← main
        \
         B ← C ← add-drinks

بعد:   A ← B ← C ← main, add-drinks
```

## دمج حقيقي (Merge commit)

إذا تقدّم الفرعان كلٌّ في طريقه، يحتاج Git لإنشاء **commit دمج** له أبوان، يجمع العملين:

```terminal
$ git switch -c add-desserts
Switched to a new branch 'add-desserts'
$ echo "كنافة" > desserts.txt
$ git add desserts.txt
$ git commit -m "قائمة الحلويات"
[add-desserts 3b88e71] قائمة الحلويات
 1 file changed, 1 insertion(+)
 create mode 100644 desserts.txt
$ git switch main
Switched to branch 'main'
$ echo "مفتوح من 8 صباحاً" > hours.txt
$ git add hours.txt
$ git commit -m "إضافة ساعات العمل"
[main 8a32a5b] إضافة ساعات العمل
 1 file changed, 1 insertion(+)
 create mode 100644 hours.txt
$ git merge add-desserts
Merge made by the 'ort' strategy.
 desserts.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 desserts.txt
$ git log --oneline -4
50becb1 (HEAD -> main) Merge branch 'add-desserts'
8a32a5b إضافة ساعات العمل
3b88e71 (add-desserts) قائمة الحلويات
e46c381 (add-drinks) إضافة الشاي
$ ls
desserts.txt  hours.txt  menu.txt
```

```text
        D ← main (ساعات العمل)
       /      \
  ... C        M ← main بعد الدمج
       \      /
        E ← add-desserts
```

الـ commit `M` هو commit الدمج، ورسالته الافتراضية `Merge branch 'add-desserts'`. والنتيجة: `main` فيه الآن الملفان معاً.

## فحص commit الدمج

```terminal
$ git log -1
commit 50becb11d715a63a4f73ce71015fc4249159b073 (HEAD -> main)
Merge: 8a32a5b 3b88e71
Author: CodeWay Student <student@codeway.dev>
Date:   Mon Jan 6 10:06:00 2025 +0300

    Merge branch 'add-desserts'
```

السطر `Merge:` يُظهر الأبوين: آخر commit في `main` وآخر commit في `add-desserts`.

## بعد الدمج

```terminal
$ git merge add-desserts
Already up to date.
$ git branch -d add-drinks
Deleted branch add-drinks (was e46c381).
$ git branch -d add-desserts
Deleted branch add-desserts (was 3b88e71).
```

دمج نفس الفرع مرة ثانية لا يفعل شيئاً: `Already up to date`. وبعد الدمج يمكن حذف الفروع بأمان.

> 💡 قاعدة الاتجاه: `git merge X` تعني «أدخل X في الفرع الذي أقف عليه». لذلك انتقل دائماً للفرع المستقبِل أولاً.

## ملخص الدرس

- للدمج: انتقل للفرع المستقبِل، ثم `git merge اسم-الفرع`.
- Fast-forward: لا commit جديد، فقط تقديم المؤشر.
- إذا تفرّع التاريخ، يُنشأ commit دمج له أبوان.
- احذف الفروع المدموجة بـ `git branch -d`.

## متى يحدث التعارض؟

Git يدمج تلقائياً معظم الوقت: إذا عدّل فرع ملفاً والفرع الآخر ملفاً مختلفاً، أو حتى أجزاء مختلفة. لكن إذا **عدّل الفرعان نفس الجزء من نفس الملف بطريقتين مختلفتين**، لا يستطيع Git أن يقرر نيابة عنك، فيتوقف ويطلب منك الحل. هذا هو **التعارض (merge conflict)**.

> 💡 التعارض ليس خطأً ولا كارثة. هو سؤال من Git: «أي النسختين تريد؟». المحترفون يحلونه يومياً.

## صناعة تعارض

```terminal-new
$ git init
Initialized empty Git repository in /project/.git/
$ echo "السعر: 100 ريال" > price.txt
$ git add .
$ git commit -m "السعر الأساسي"
[main (root-commit) 5a98ce2] السعر الأساسي
 1 file changed, 1 insertion(+)
 create mode 100644 price.txt
$ git switch -c discount
Switched to a new branch 'discount'
$ echo "السعر: 80 ريال" > price.txt
$ git commit -am "خصم 20%"
[discount 3830e0a] خصم 20%
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git switch main
Switched to branch 'main'
$ echo "السعر: 120 ريال" > price.txt
$ git commit -am "رفع السعر"
[main 7ac7da6] رفع السعر
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git merge discount
Auto-merging price.txt
CONFLICT (content): Merge conflict in price.txt
ERR: Automatic merge failed; fix conflicts and then commit the result.
```

## قراءة علامات التعارض

```terminal
$ git status
On branch main

You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   price.txt
$ cat price.txt
<<<<<<< HEAD
السعر: 120 ريال
=======
السعر: 80 ريال
>>>>>>> discount
```

Git كتب النسختين داخل الملف بعلامات خاصة:

| العلامة | المعنى |
|---|---|
| `<<<<<<< HEAD` | بداية نسختك (الفرع الحالي) |
| `=======` | الفاصل بين النسختين |
| `>>>>>>> discount` | نهاية نسخة الفرع المدموج |

## حل التعارض

الحل ثلاث خطوات:

1. **عدّل الملف** ليحتوي النتيجة النهائية التي تريدها، واحذف العلامات الثلاث.
2. **أخبر Git أنك حللته** بـ `git add`.
3. **أكمل الدمج** بـ `git commit`.

قررنا اعتماد السعر الجديد مع الخصم:

```terminal
$ echo "السعر: 96 ريال" > price.txt
$ git add price.txt
$ git status
On branch main

All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   price.txt
$ git commit -m "دمج الخصم مع السعر الجديد"
[main bb65b23] دمج الخصم مع السعر الجديد
$ git log --oneline
bb65b23 (HEAD -> main) دمج الخصم مع السعر الجديد
7ac7da6 رفع السعر
3830e0a (discount) خصم 20%
5a98ce2 السعر الأساسي
```

## ملفات بعدة أسطر: heredoc

في الواقع ستحل التعارض في محرّرك (VS Code يعرض أزراراً مثل Accept Current و Accept Incoming). في الطرفية، يمكنك كتابة ملف من عدة أسطر بصيغة **heredoc**:

```terminal-new
$ cat > menu.txt <<EOF
> قهوة: 15
> شاي: 5
> EOF
$ cat menu.txt
قهوة: 15
شاي: 5
```

كل ما بين السطر الأول و `EOF` يُكتب في الملف. في محرر التمرين تكتب الأسطر مباشرة دون علامة `>`.

## التراجع عن الدمج

إذا شعرت أن الأمور تعقّدت وتريد البدء من جديد:

```terminal-new
$ git init
Initialized empty Git repository in /project/.git/
$ echo "v1" > a.txt
$ git add .
$ git commit -m "v1"
[main (root-commit) 70d4e01] v1
 1 file changed, 1 insertion(+)
 create mode 100644 a.txt
$ git switch -c other
Switched to a new branch 'other'
$ echo "v2-other" > a.txt
$ git commit -am "other"
[other 3bd54a3] other
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git switch main
Switched to branch 'main'
$ echo "v2-main" > a.txt
$ git commit -am "main"
[main 9af9d19] main
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git merge other
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
ERR: Automatic merge failed; fix conflicts and then commit the result.
$ git merge --abort
$ git status
On branch main

nothing to commit, working tree clean
```

`git merge --abort` يعيد كل شيء كما كان قبل الدمج.

## نصائح لتقليل التعارضات

- ادمج `main` في فرعك باستمرار ولا تترك الفرع يعيش أسابيع.
- اجعل الفروع صغيرة ومركزة على مهمة واحدة.
- تواصل مع فريقك إذا كنتم ستعدّلون نفس الملفات.

## ملخص الدرس

- التعارض يحدث عند تعديل نفس الجزء من نفس الملف في الفرعين.
- العلامات `<<<<<<<` و `=======` و `>>>>>>>` تحيط بالنسختين.
- الحل: عدّل الملف ← `git add` ← `git commit`.
- `git merge --abort` يلغي الدمج ويعيد الحالة السابقة.

## طريقة أخرى للدمج: rebase

`git merge` يحفظ التاريخ كما حدث فعلاً، بتفرعاته و commits الدمج. أما `git rebase` فيعيد كتابة تاريخ فرعك **كأنك بدأته من آخر نقطة في main**، فيصبح التاريخ خطاً مستقيماً نظيفاً.

```text
قبل rebase:              بعد git rebase main:

      D ← main                 D ← main
     /                          \
A ← B                            C' ← feature
     \
      C ← feature
```

الـ commit `C` نُسخ فوق `D` كـ commit جديد `C'` بنفس التغييرات ومعرّف مختلف.

## merge أم rebase؟

| | merge | rebase |
|---|---|---|
| التاريخ | حقيقي بكل تفرعاته | خط مستقيم نظيف |
| commits الدمج | يضيفها | لا يضيفها |
| يغيّر المعرّفات | لا | نعم، ينشئ commits جديدة |
| آمن على الفروع المشتركة | دائماً | لا |

## القاعدة الذهبية

> ⚠️ لا تعمل rebase أبداً على commits رفعتها ويعمل عليها غيرك. rebase ينشئ commits جديدة، فيصبح تاريخك مختلفاً عن تاريخ زملائك وتحدث فوضى.

الاستخدام الآمن والشائع: تحديث **فرعك الشخصي** بآخر ما في `main` قبل فتح Pull Request:

```bash
git switch feature/my-task
git rebase main
```

## ملخص الدرس

- `git rebase main` يعيد بناء commits فرعك فوق آخر `main`.
- النتيجة تاريخ مستقيم، ودمج لاحق بـ Fast-forward.
- rebase ينشئ commits جديدة بمعرّفات جديدة.
- استخدمه على فروعك الخاصة فقط، وليس على ما يشاركك فيه الآخرون.

--- quiz
? ما الفرق الأساسي بين merge و rebase؟
+ merge يحفظ التاريخ بتفرعاته وقد يضيف commit دمج، و rebase يعيد كتابة commits فرعك فوق الفرع الآخر في خط مستقيم
- لا فرق في النتيجة
- rebase يحذف التغييرات
> كلاهما يجمع التغييرات، لكن شكل التاريخ يختلف.

? لماذا يتغير معرّف الـ commit بعد rebase؟
- خطأ في Git
+ لأن rebase ينشئ commits جديدة بنفس التغييرات فوق أب مختلف
- لأن الرسالة تغيرت
> المعرّف يعتمد على المحتوى والأب، والأب تغيّر.

? متى يكون rebase خطيراً؟
+ على commits رفعتها ويعمل عليها أشخاص آخرون
- على فرعك المحلي الذي لم يره أحد
- عندما يكون الفرع جديداً
> القاعدة الذهبية: لا rebase على التاريخ المشترك.
