=== lesson
## الاختبار الشامل (End-to-End)

اختبارات الوحدات والمكونات تختبر الأجزاء منفصلة. لكن هل يعمل **التطبيق كاملاً** كما يستخدمه الناس؟ هل صفحة الدخول تنقلك فعلاً للوحة التحكم؟ **الاختبار الشامل** يفتح متصفحاً حقيقياً، ويزور موقعك، وينقر ويكتب كالإنسان تماماً.

**Playwright** من Microsoft الأداة الأقوى اليوم لذلك:

- يختبر على **Chromium و Firefox و WebKit (Safari)** بنفس الكود.
- **ينتظر تلقائياً**: لا ينقر زراً قبل ظهوره وجاهزيته، فلا تحتاج `sleep`.
- أدوات رائعة: وضع واجهة رسومية `--ui`، وتسجيل الخطوات، وتقرير HTML بلقطات شاشة عند الفشل.

> 💡 البديل المعروف **Cypress**، وما زال مستخدماً في مشاريع كثيرة. المفاهيم متشابهة جداً.

## التثبيت

```bash
npm init playwright@latest
```

ينشئ `playwright.config.js` ومجلد `tests` (أو `e2e`) ويثبّت المتصفحات. والتشغيل:

```bash
npx playwright test          # كل الاختبارات
npx playwright test --ui     # واجهة رسومية تعرض كل خطوة
npx playwright show-report   # تقرير HTML بعد التشغيل
```

```testfiles
  await page.goto("/");
  await page.getByRole("link", { name: "تصفح الدورات" }).click();
  await expect(page).toHaveURL("/courses");
  await expect(page.getByRole("listitem")).toHaveCount(3);
```

- كل اختبار يستلم `page`: تبويب متصفح جديد ونظيف.
- **Locators** مثل `page.getByRole(...)` تشبه استعلامات Testing Library تماماً.
- **التحققات تعيد المحاولة**: `toHaveText` ينتظر حتى يصبح النص صحيحاً (أو تنتهي المهلة)، فلا مشاكل توقيت.

## الأفعال الأساسية

| الفعل | مثال |
|---|---|
| الزيارة | `await page.goto("/login")` |
| النقر | `await page.getByRole("button", { name: "حفظ" }).click()` |
| الكتابة | `await page.getByLabel("البريد").fill("a@b.com")` |
| مفتاح | `await page.getByLabel("البحث").press("Enter")` |
| الاختيار | `await page.getByLabel("المدينة").selectOption("riyadh")` |
| مربع اختيار | `await page.getByRole("checkbox").check()` |

## تحققات تنتظر تلقائياً

| التحقق | ينتظر حتى |
|---|---|
| `toBeVisible()` | يظهر العنصر |
| `toHaveText("...")` و `toContainText` | يطابق النص |
| `toHaveCount(n)` | يصبح العدد n |
| `toHaveValue("...")` | قيمة الحقل |
| `expect(page).toHaveURL("/x")` | يتغير الرابط |
| `expect(page).toHaveTitle("...")` | عنوان الصفحة |

## ملخص الدرس

- الاختبار الشامل يختبر التطبيق كاملاً في متصفح حقيقي كما يستخدمه الناس.
- Playwright: `page.goto` و locators مثل `getByRole` و `getByLabel`، وأفعال مثل `click` و `fill`.
- التحققات تنتظر تلقائياً، فلا حاجة لتأخيرات يدوية.
- `npx playwright test --ui` لمشاهدة الاختبار خطوة بخطوة.

--- exercise
صفحة الدخول `site/login.html` جاهزة: إذا أُدخل البريد `admin@codeway.dev` وكلمة المرور `123456` ثم ضُغط زر `دخول`، تظهر رسالة `أهلاً بك يا مدير`، وإلا تظهر `بيانات الدخول غير صحيحة`.

اكتب `e2e/login.spec.js` باختبارين:

1. دخول ناجح يُظهر رسالة الترحيب.
2. كلمة مرور خاطئة تُظهر رسالة الخطأ.

استخدم `getByLabel` للحقول، و `getByRole("button", { name: "دخول" })` للزر، و `getByRole("alert")` للرسالة.

~~~setup
document.getElementById("f").addEventListener("submit", (e) => {
~~~

--- quiz
? ما الذي يميز الاختبار الشامل عن اختبار الوحدة؟
+ يختبر التطبيق كاملاً في متصفح حقيقي كما يستخدمه الإنسان
- أسرع من اختبار الوحدة
- لا يحتاج متصفحاً
> لذلك هو أبطأ ونخصصه للمسارات المهمة.

? لماذا لا تحتاج في Playwright لتأخير مثل `sleep(2000)` قبل التحقق؟
+ لأن التحققات والأفعال تنتظر تلقائياً حتى يجهز العنصر أو تتحقق الحالة
- لأن المتصفح سريع دائماً
- لأن sleep غير مدعوم
> التأخيرات اليدوية تجعل الاختبارات بطيئة ومتقلبة.

? كيف تكتب في حقل عنوانه «الاسم»؟
+ `await page.getByLabel("الاسم").fill("سارة")`
- `page.type("الاسم", "سارة")`
- `await page.fill("سارة")`
> getByLabel يجد الحقل بنص label المرتبط به.

## اختبار السيناريوهات

أقوى الاختبارات الشاملة تحكي **قصة مستخدم كاملة**: «يدخل الزائر المتجر، يضيف منتجين للسلة، يذهب للدفع، فيرى تأكيد الطلب». إذا نجح هذا السيناريو، فأهم مسار في عملك يعمل.

أمثلة سيناريوهات تستحق الاختبار:

- التسجيل وتسجيل الدخول.
- البحث عن منتج وإضافته للسلة وإتمام الشراء.
- نشر تعليق وظهوره للآخرين.

## تنظيم السيناريو

```testfiles
    await expect(page.getByRole("listitem")).toHaveCount(2);
    await expect(page.getByRole("listitem").first()).toHaveText("تعلم JavaScript");

    await page.getByRole("button", { name: "ادفع الآن" }).click();
```

## محاكاة الشبكة: page.route

الصفحات الحقيقية تجلب بياناتها من واجهة برمجية. في الاختبار نريد بيانات **ثابتة ومعروفة**، ونريد اختبار حالات يصعب إحداثها: خادم معطل أو قائمة فارغة. `page.route` يعترض الطلبات ويرد بما نريد:

```testfiles
// file: site/index.html
<!doctype html>
<html lang="ar" dir="rtl">
<head><title>المنتجات</title></head>
<body>
  <h1>المنتجات</h1>
  <ul id="list"><li>جاري التحميل...</li></ul>
  <script src="app.js"></script>
</body>
</html>
// file: site/app.js
const list = document.getElementById("list");
fetch("/api/products")
  .then((r) => { if (!r.ok) throw new Error(); return r.json(); })
  .then((products) => {
    list.innerHTML = products.length
      ? products.map((p) => `<li>${p.name} - ${p.price} ر.س</li>`).join("")
      : "<li>لا توجد منتجات</li>";
  })
  .catch(() => { list.innerHTML = '<li role="alert">تعذّر تحميل المنتجات</li>'; });
// file: e2e/products.spec.js
import { test, expect } from "@playwright/test";

test("يعرض المنتجات من الواجهة", async ({ page }) => {
  await page.route("**/api/products", (route) =>
    route.fulfill({ json: [{ name: "قلم", price: 5 }, { name: "دفتر", price: 15 }] })
  );
  await page.goto("/");
  await expect(page.getByRole("listitem")).toHaveCount(2);
  await expect(page.getByRole("listitem").first()).toHaveText("قلم - 5 ر.س");
});

test("قائمة فارغة", async ({ page }) => {
  await page.route("**/api/products", (route) => route.fulfill({ json: [] }));
  await page.goto("/");
  await expect(page.getByText("لا توجد منتجات")).toBeVisible();
});

test("الخادم معطل", async ({ page }) => {
  await page.route("**/api/products", (route) => route.fulfill({ status: 500 }));
  await page.goto("/");
  await expect(page.getByRole("alert")).toHaveText("تعذّر تحميل المنتجات");
});
```

## نصائح لاختبارات شاملة موثوقة

- **كل اختبار مستقل**: لا تعتمد على بيانات تركها اختبار سابق.
- **اختبر من منظور المستخدم**: بالأدوار والنصوص، لا بالأصناف والمعرّفات الداخلية.
- **ركّز على المسارات المهمة**: الاختبار الشامل مكلف، فلا تكرر فيه ما تغطيه اختبارات الوحدات.
- **تجنّب التأخيرات الثابتة**: اعتمد على الانتظار التلقائي للتحققات.

## ملخص الدرس

- السيناريو يختبر قصة مستخدم كاملة عبر عدة صفحات.
- `test.describe` و `test.beforeEach` لتنظيم الاختبارات وتجهيزها.
- `first()` و `nth()` و `filter()` لاختيار عنصر من عدة عناصر.
- `page.route` يحاكي الواجهة البرمجية لبيانات ثابتة واختبار حالات الخطأ والقوائم الفارغة.

--- exercise
صفحة البحث `site/index.html` تجلب نتائج من `/api/search?q=...` عند كتابة كلمة والضغط على Enter في حقل `ابحث`، وتعرض كل نتيجة كعنصر قائمة، أو `لا توجد نتائج`، أو رسالة `تعذّر البحث` بدور `alert` عند فشل الخادم.

اكتب `e2e/search.spec.js` بثلاثة اختبارات تستخدم `page.route` على `**/api/search*`:

1. نتيجتان: يظهر عنصرا قائمة، والأول نصه `Next.js للمبتدئين`.
2. استجابة فارغة `[]`: يظهر `لا توجد نتائج`.
3. حالة 500: تظهر رسالة الخطأ.

~~~setup
// file: site/index.html
<!doctype html>
<html lang="ar" dir="rtl">
<head><title>البحث</title></head>
<body>
  <label for="q">ابحث</label>
  <input id="q" type="search">
  <ul id="results"></ul>
  <script src="search.js"></script>
</body>
</html>
// file: site/search.js
const input = document.getElementById("q");
const results = document.getElementById("results");
input.addEventListener("keydown", async (e) => {
  if (e.key !== "Enter") return;
  try {
    const res = await fetch("/api/search?q=" + encodeURIComponent(input.value));
    if (!res.ok) throw new Error();
    const items = await res.json();
    results.innerHTML = items.length ? items.map((t) => `<li>${t}</li>`).join("") : "<li>لا توجد نتائج</li>";
  } catch {
    results.innerHTML = '<li role="alert">تعذّر البحث</li>';
  }
});
~~~

=== lesson
## التكامل المستمر (CI)

الاختبارات لا تفيد إن لم تُشغَّل. والإنسان ينسى. **التكامل المستمر (Continuous Integration)** يشغّل الاختبارات تلقائياً على خادم مع كل push و Pull Request:

- لا يُدمج كود يكسر الاختبارات.
- المراجع يرى النتيجة على الـ PR مباشرة: ✓ أو ✗.
- نفس البيئة للجميع: «يعمل على جهازي» لم تعد حجة.

**GitHub Actions** خدمة CI مدمجة في GitHub ومجانية للمستودعات العامة. تُعرّف في ملفات YAML داخل `.github/workflows/`.

## أول Workflow

```testfiles
// file: package.json
{
  "scripts": { "test": "vitest run" },
  "devDependencies": { "vitest": "^3.2.4" }
}
// file: package-lock.json
{}
// file: sum.js
export const sum = (a, b) => a + b;
// file: sum.test.js
import { it, expect } from "vitest";
import { sum } from "./sum.js";
it("يجمع", () => expect(sum(2, 3)).toBe(5));
// file: .github/workflows/test.yml
name: Tests

on:
  push:
    branches: [main]
  pull_request:

jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm test
// test
await ci("pull_request");
```

```output

▶ unit (ubuntu-latest)
   ✓ Set up job
   ✓ Run actions/checkout@v4
   ✓ Run actions/setup-node@v4  (Node.js 22)
```

اقرأ الملف من الأعلى:

| الجزء | المعنى |
|---|---|
| `name` | الاسم الظاهر في تبويب Actions |
| `on` | متى يعمل: push إلى `main`، وكل Pull Request |
| `jobs` | المهام، وكل مهمة تعمل على جهاز مستقل |
| `runs-on` | نظام الجهاز: `ubuntu-latest` الأشهر والأرخص |
| `steps` | الخطوات بالترتيب |
| `uses` | خطوة جاهزة: `checkout` ينزّل الكود، و `setup-node` يثبّت Node.js |
| `run` | أمر طرفية |

> 💡 `npm ci` بدل `npm install` في CI: يثبّت من `package-lock.json` حرفياً وبسرعة. و `cache: npm` يحفظ الحزم بين التشغيلات فيصبح أسرع بكثير.

> ⚠️ المسافات في YAML هي البنية نفسها: مسافتان لكل مستوى، ولا تستخدم Tab أبداً.

## اختبارات Playwright في CI

الاختبارات الشاملة تحتاج متصفحات، فنثبّتها بخطوة إضافية، ونرفع التقرير حتى عند الفشل لنعرف السبب:

```yaml
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
```

`if: always()` يجعل الخطوة تعمل حتى لو فشل ما قبلها، فتحصل على التقرير بلقطات الشاشة.

## حماية الفرع الرئيسي

الخطوة الأخيرة لاحترافية كاملة: في إعدادات المستودع على GitHub **Settings → Branches → Branch protection rules**، فعّل **Require status checks to pass before merging** واختر مهام CI. الآن لا يستطيع أحد دمج Pull Request تفشل اختباراته.

## ملخص الدرس

- CI يشغّل الاختبارات تلقائياً مع كل push و Pull Request.
- GitHub Actions: ملفات YAML في `.github/workflows/` فيها `on` و `jobs` و `steps`.
- الخطوات المعتادة: `checkout` ثم `setup-node` ثم `npm ci` ثم الاختبارات.
- لـ Playwright: `npx playwright install --with-deps`، ورفع التقرير بـ `if: always()`.
- حماية الفرع تمنع دمج كود تفشل اختباراته.
